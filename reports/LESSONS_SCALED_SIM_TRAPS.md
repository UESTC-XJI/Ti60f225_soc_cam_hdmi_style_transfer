# 缩比仿真通过、真实几何失败 —— 三次同型故障的复盘

> 2026-10-28
> 这份文档只讲一件事：**为什么"小几何仿真通过"不能证明"大几何正确"**。
> 本项目至今已经因为同一个原因栽了三次，每次都是上板才暴露。

---

## 一 共同模式

```
在 TB_TINY / 小帧 / 少量 beat 的配置下仿真 → 通过
换成生产几何（640×480 / 320 宽 / 80 beat 每行）→ 静默错误
```

**根因永远是同一个：某个字段/计数器/参数是按"小配置"写的死数或窄位宽，
小配置下够用，大配置下回绕 / 溢出 / 别名。**

这类 bug 的共同特征：

| 特征 | 说明 |
|---|---|
| **不报错** | 编译通过、综合通过、时序也正 |
| **仿真在小配置下也过** | 因为值没到临界点 |
| **只在上板或大帧仿真时暴露** | 而且往往表现为"画面坏了但 error=0" |
| **修好之后看 diff 极其显然** | 一个常量换成派生表达式 |

## 二 案例 1：`CI*8` 的双语义（2026-10-27）

```verilog
// rowpipe_layer.v —— 同一个 CI*8 在 6 个地方代表两种东西
input  wire [CI*8-1:0] s_col,    // 实际语义：一个像素的 CI 个通道字节
output wire [CI*8-1:0] o_id,     // 通道宽（对）
localparam OW = CO*8 + CI*8 + 2; // 含 o_id，所以是通道宽（对）
localparam CW = CI*8;            // 行缓冲存通道（对）
```

**为什么当时没出错**：`CI == PIX == 16`，所以 `CI*8` 和 `PIX*8` 都等于 128，
写错看不出。审计报告说"CI/CO 16→8 只改一行"，实际逐处核对才发现有 6 处、两种语义。

**教训**：**"两个参数恰好相等"是最危险的巧合**。它会掩盖所有把 A 当 B 用的错误。

**现状**：已改成显式 `PIX*8`，并在注释里写清每个宽度的语义。

## 三 案例 2：`IDXW = 6` 写死（2026-10-28，B-1 实验暴露）

```verilog
// rowpipe_ddr_banks.v —— 两个几乎一模一样的 FIFO 模块
module rowpipe_rd_stream #(parameter DEPTH = ...)
    localparam integer IDXW = clogb2(DEPTH);   // ✓ 随 DEPTH 变

module rowpipe_src_stream #(parameter DEPTH = 64)
    localparam integer IDXW = 6;                // ✗ 只够 DEPTH=64
```

**为什么当时没出错**：`DEPTH` 一直是 64，`clogb2(64) == 6` ✓ 恰好对上。

**怎么暴露的**：B-1 实验把 `DEPTH` 改成 256 想让 src burst 更长。
`wr_idx/rd_idx` 仍只有 6 位 ⇒ **指针在 64 处回绕、别名** ⇒ FIFO 实际只用 64 个槽位且错位
⇒ 数据静默错乱。仿真表现为 L0 的逐层写入哈希与基线不符。

**这个 bug 的价值**：它说明 **B-1 那次"负面结果"其实是被这个隐藏 bug 污染的结果**——
我据此撤回了 B-1，但真实原因可能是 IDXW 而不是 MAXB。

**教训**：**写死的常量在参数化模块里是定时炸弹**。凡是被 `parameter` 影响的位宽，
必须用 `clogb2(DEPTH)` 之类派生，不能写死。

**现状**：已改成 `clogb2(DEPTH)`（`clogb2` 在 `src_stream` 内另备了一份，
因为它原本只定义在 `rd_stream` 内部）。

**附带修掉的第二个**：`free_ok = ((count + inflight) < (DEPTH - 32))` —— 那个 `-32`
是按 `MAXB=8` 配平写死的（`bst_words = bst_beats*4`）。改 `MAXB` 而不改它，
`count+inflight` 能冲过 `DEPTH` ⇒ **FIFO 溢出 ⇒ 静默错图**。已改成 `DEPTH - MAXB*4`。

## 四 案例 3：A-3 的 2×2 复制（2026-10-28，**上板当场抓出**）

A-3 把 L11 降到 320×240、在**写通道**做 2×2 复制维持 640×480 契约。

**TINY 仿真**：结构判据全绿
```
水平成对 768/768、垂直成对 24/24、wr_beats=2,880 手工对账吻合
```
**上板实际**：
```
行 0: ✅ 全部正确
行 1: ❌ 384 个像素是垃圾（X 字节非 0）
行 2: ✅
行 3: ❌ 512 个像素是垃圾
```

**偶数行对、奇数行错** —— 垂直复制那一半坏掉，而且坏得"部分正确"，
所以逐像素哈希类判据（在小几何下）也未必抓到。

**为什么 TINY 没抓到**：TINY 是 **8 源 beat/行**，生产是 **80 源 beat/行**。
某个与"每行 beat 数"相关的计数/地址计算在 8 下不会溢出，在 80 下会。

**处理**：A-4 把这套复制逻辑**整个删掉**，改由显示端做 2× 放大
⇒ bug 的载体消失。上板验证：MS 26 ms、UF/FAULT 归零、画面正常。

**教训**（这条最硬）：
> **任何"每行/每帧的循环次数"相关的逻辑，都必须用生产几何验证一次。**
> `TB_TINY` 能验数据通路和控制流，但**验不了宽度/计数溢出**。

## 五 已经采取的防线

| 防线 | 内容 |
|---|---|
| **`build_check.py`** | 每次构建必查时序正负 + 面积告警，不只看 `pnr: PASS` |
| **隔离式 A/B** | 快照编译 + 只替换待测文件，55 秒级，能逐位比对 |
| **结构判据优先于哈希** | A-3 的结构判据（水平/垂直成对率）比最终哈希更能定位问题；A-3 开发中就是靠它抓到两个"画面全黑但 error=0"的 bug |
| **板级第一眼** | 上板先看 `UF`/`FAULT`/`AXI`/`PF==PFC` 四个数 + 抓一张图，比看任何日志快 |
| **单一来源参数** | A-3 的 `RESULT_X2` 与 `TAIL_LOWRES` 原本是跨文件成对约束，已打通成 `style_accel → network → frame_driver → banks` 一条链，物理上不可能失配 |

---

## 六 还欠的一道防线（建议加，未做）

**给 `TB_TINY` 之外补一个"生产几何的最小冒烟仿真"**——不必跑完整帧（太慢，35 分钟），
只需：

- 用**生产的宽度常数**（320 源 beat/行、640 目标宽）但**只跑 1~2 行**
- 断言：每行 beat 数、地址递增、X 字节为 0、成对关系

这样能在 1~2 分钟内覆盖"宽度相关"的那类 bug，而 `TB_TINY` 覆盖控制流。
**两者互补，缺一不可。**

A-3 的 bug 如果用这个冒烟台跑，会在上板前就被抓住。

---

## 七 一句话

**小几何验证控制流，生产几何验证位宽。**
凡是"循环次数 = 每行像素数/beat 数"的地方，缩比仿真通过**不构成任何证据**。
