# 视频前后端逐行阅读

> 范围：CSI 接收接口 → gearbox → debayer（5 个 RTL + 1 个 RAM 宏）→ style_vga_crop → DDR，以及显示侧的 tone/lift/AE 统计。
> 方法：逐行通读源码（`read` 分段读完），宏值与相位用 `defines.v` 反查，LUT 用脚本全量 dump 验证。
> 只读分析，未修改任何 RTL / 固件 / 工程文件，未跑综合。
> 三个真实时钟沿用 Lead 已核对的事实：`core_clk` 100 MHz、`vid_clk_dvi2` 148.5 MHz、`hdmi_tx_slow_clk` 74.25 MHz；采集侧另有 `i_mipi_rx_pclk`（CSI pixel clock，约 50 MHz）与 `i_mipi_clk`。

## 结论摘要（5 条）

1. **debayer 的相位（Bayer 相位）是自洽的，文档问题 3 的假设（"`gain_g` 在奇偶行都用所以 G 通道不对称"）不成立。** `rgb_gain_v1.v:75-89` 的 `!GREEN_FIRST` 分支对 BGGR 是**逐像素恰好乘一次增益**：偶行 `low=B×gain_b / high=G×gain_g`，奇行 `low=G×gain_g / high=R×gain_r`。`gain_g` 出现两次是因为绿像素在奇偶行都物理存在，这是 Bayer 的固有属性，不是通道不对称；R/B 也只各用一次（同样正确）。**每像素只乘一次，模块只实例化一次，无重复乘、无通道互换。**
2. **`raw_to_rgb` 的双线性核也是对的**，但它的行选相是"用 `r_y_cnt[0]` 选公式、而公式作用在中心行 `n-1` 上"（`raw_to_rgb.v:352`）。由于输出行号恰好等于 `r_y_cnt-1`，这两个"错一拍"互相抵消，BGGR 下奇/偶行公式与物理行型对得上。这是一个**依赖 ±1 行对齐才正确的脆弱设计**，任何多/少一行都会整体翻相。
3. **G/R σ 比：debayer/rgb_gain 的结构能解释 1.06（模型侧），不能解释 1.95（板上）。** 解析计算：双线性核使 G 通道 50% 单点 + 50% 四点平均（α_G=√0.625=0.7906），R 通道 25% 单点 + 50% 两点 + 25% 四点（α_R=√0.5625=0.75），固有比 **1.054**，与模型侧 1.06 吻合到 1%；而该比值对任意场景相关性都被限制在 **1.00~1.06** 区间，**结构上不可能到 1.95**。
4. **能定量解释 1.95 的是 AWB 增益 + 255 硬截断，不是相位。** 固件把 R/B 设成 520（=2.03×）、G 设 290（=1.13×）；`rgb_gain_v1.v:92-93` 的饱和条件是 `|mul[23:16]`，等价 `v≥126` 时 R/B 就夹到 255，而 G 要到 `v≥226` 才夹。AE 把 G 均值压到 100~140 时，R/B 会有很大比例落在饱和区 → **σ_R、σ_B 被削掉、σ_G 不动**。实测形状 `σ_G=44.9 ≫ σ_R=23.0 ≈ σ_B=26.1` 与该预测完全吻合（R、B 恰是同一档增益的两个通道）。置信度：中高，**需读源帧 0x05000000 的三通道均值 + 255 占比确认**（判决性实验，见末节）。
5. **两处必须记录的实现事实**：① tone/lift/AE 全部在 **显示域 74.25 MHz、帧缓冲之后**，不可能影响 `0x05800000` 的 σ；② `rtl/isp/capture_frame_stats.sv` 被 `include` 进顶层但**从未实例化**（死代码），真正在跑的是 `video_apb_ctrl.sv` 内自带的统计算法。另外 `luma_tone_map` 的输出乘法**没有显式饱和**，安全性完全依赖 `lift_cap/lift_safe_cap` 表满足 `v×factor ≤ 65535`（已全量验证成立，最大 65280，余量仅 255）。

**debayer_total 端到端延迟**：1（gain）+ 2（line_buffer）+ 2（raw_to_rgb）= **5 拍**，另加**1 行**垂直延迟（中心行 = 输入行 n−1）。
**相位结论（BGGR 判定）**：`raw_datax4_i[7:0]` = 同行**先到**的像素（偶列），`[15:8]` = 后到的像素（奇列）；偶行 low=B/high=G、奇行 low=G/high=R ⇒ 行 0 为 `B G B G`，即 **BGGR**，与 `top.v:804-806` 注释"measured white: green 在 even/high 与 odd/low"、`CAM_RAW_GREEN_FIRST=0`、`defines.v` 的 `CFG_TI60F225_OOB_TOP_V_LOCALPARAM_CAM_RAW_GREEN_FIRST 1'b0` 三者一致。

### CSI 40 位 → 4 个 RAW8 的映射（Lead 要求确认）

`ti60f225_oob_top.v:559`：
```verilog
.s_data({w_mipi_rx_data[39:32],w_mipi_rx_data[29:22],
         w_mipi_rx_data[19:12],w_mipi_rx_data[9:2]}),
```
* 断言：`pixel_data` 低 40 位按 **4×10 位**打包，`sample_k = pixel_data[10k+9 : 10k]`，`k=0..3`。
* 切片取 `{sample3[9:2], sample2[9:2], sample1[9:2], sample0[9:2]}` ⇒ **每字节高 8 位、丢低 2 位**（RAW10→RAW8 截断，等价 `>>2`）。**此理解正确**，且被 `capture_frame_stats.sv:3` 的注释独立佐证："Native RAW is 8 bits here: the CSI gearbox already discarded RAW10 bits 1:0"。
* **lane 映射**：4 lane 并行 → 一拍 4 个相邻像素，`sample0` = 该拍**最早**的像素（lane0），`sample3` 最晚。随后的 gearbox 把 `q[15:0]`（= `{sample1,sample0}`）先输出 ⇒ `d_data[7:0]=sample0`（偶列）、`d_data[15:8]=sample1`（奇列），**每拍 2 像素、低字节在前**，与全链路"low=偶列"的约定一致。
* ⚠️ "sample0 = 最早像素"这一条是**推断**（由图像正确性反推），源码里没有显式断言；若 CSI IP 实际是逆序打包，则列相位会翻转（见 G/R 调查 H1）。

### 时钟只有 3 个主时钟的说法需要打补丁
Lead 给的"真实时钟只有 3 个"对**处理链**成立，但采集入口还有 2 个物理时钟：`i_mipi_clk`（CSI IP 的 `clk`/`axi_clk`）与 `i_cam_ck_CLKOUT`（`clk_byte_HS`）。`csi_rx_controller` 的参数里 `HS_BYTECLK_MHZ=70`、`CLOCK_FREQ_MHZ=100`，`clk_pixel` 由 IP 内部分频得到 ≈50 MHz（`top.v:423`）。所以严格说是 **5 个时钟域**（mipi_clk / byte_HS / pclk / vid_clk_dvi2 / hdmi_tx_slow_clk），跨域点 3 处：CSI 内部、gearbox 异步 FIFO、视频配置/AE 的 mailbox。

### 2. `rtl/resize/camera_raw_gearbox.v`（75 行主体 + 40 行 FIFO）

**职责与契约**：把 CSI 的 **4 RAW8/拍 @50 MHz** 转成 **2 RAW8/拍 @148.5 MHz**，并用"整行先入队再回放"的方式给老式 debayer 提供**连续 DE**。位置：CSI 之后、debayer 之前，是采集链唯一的异步跨界点之一。

**端口**

| 端口 | 方向 | 位宽 | 域 | 语义 |
|---|---|---|---|---|
| `s_clk/s_rst_n` | in | 1 | `i_mipi_rx_pclk` | 源域 |
| `s_vs` | in | 1 | 源域 | `w_mipi_rx_vs`（帧起始） |
| `s_valid` | in | 1 | 源域 | 顶层接 `w_mipi_rx_de & w_mipi_rx_hs`（**两者相与**，见疑点） |
| `s_data` | in | 32 | 源域 | 4×RAW8（低字节 = 偶列） |
| `d_clk/d_rst_n` | in | 1 | `vid_clk_dvi2` | 目的域 |
| `d_vs/d_de` | out | 1 | 目的域 | 每行一个 `d_vs` 脉冲 + 连续 `d_de` |
| `d_data` | out | 16 | 目的域 | 2×RAW8，`[7:0]`=偶列、`[15:8]`=奇列 |
| `fault` | out | 1 | —— | `input_fault`(CDC) \| `output_fault`，顶层接 `capture_fault` |

**内部结构 / 逐行要点**
* `L14` `GROUPS = SOURCE_WIDTH/4 = 480`：一行的 32 位包数。
* `L15-24` 源侧：`first = pending_sof || fs`（`fs = vs_d && !s_vs`）；包格式 `{first, current_sx==GROUPS-1, s_data}`（34 位）；`accept = s_valid && (started || fs) && !input_fault` ⇒ **必须见过一次 VS 才开始收**。
* `L29-39` `sx` 数包、`sy` 数行；`sx==GROUPS-1` 回卷并 `sy+1`。三个**永久故障锁存**：VS 到来时上一帧没停在 `(sx==0, sy==SOURCE_HEIGHT)`、FIFO `full`、`sy>=SOURCE_HEIGHT`。
* `L47` `take = active && preamble==0 && half && valid`：**FIFO 每 2 个 d_clk 才前进 1 包**（一个 32 位包拆成 2 个输出拍）。
* `L60-62` 启动条件 `!active && valid && available>=GROUPS`（**必须攒满整行 480 包**）；`d_vs<=q[33]`，若是 SOF 则 `preamble<=6`（**6 拍空 preamble** 后才拉 DE）。
* `L63-71` 回放：`d_de<=1`；`d_data <= half ? q[31:16] : q[15:0]`；`if(half && q[32]) active<=0`（行尾包后收工）。
* `L77-117` `resize_async_fifo`：Gray 指针 + BRAM + **寄存首字**（`d_available = ungray(wg_s) − rp + d_valid` 把首字算进去），空满用标准 Gray 高位取反比较。深度 `2^10=1024` 包 ≫ 480 ✓。

**带宽/水位核算（事实）**：一行 480 包；目的侧 1 包/2 拍 = 960 d_clk ≈ 6.46 µs 排空；源侧一行 ≈ 480 包×20 ns ≈ 9.6 µs 才来一行 ⇒ **排空快于填充**，所以每行排空期间 FIFO 净减 ~157 包；靠"启动前 ≥480 包"的门槛保证不会抽干，但代价是**行末必然停顿**（`active<=0` 后要等下一行攒满）。

**风险与疑点**
| 位置 | 疑点 | 现象 | 置信度 |
|---|---|---|---|
| `L31` / `L35` | `input_fault` **只置位、永不清除**（只被 `s_rst_n` 清），且 `fault` 经 CDC 到目的域后直接让 `active<=0`（`L65`） | 一次瞬态（丢包/多一行/一次 FIFO 满）会**永久黑屏**直到复位；板侧只表现为 `led[1]` 常亮 | 高（代码事实） |
| `L24`+`top.v:558` | `s_valid = w_mipi_rx_de & w_mipi_rx_hs`。若 CSI IP 的 `hsync_vc0` 有极性与 DE 不完全重合的行为（例如行首多/少一拍），会**吞掉/多计一个包**，而 `sx` 计数错位会直接触发 `input_fault` 或让该行整体左/右移 4 像素 | 行首 4 像素级错位 → **破坏偶列/奇列相位** ⇒ 通道旋转（见 G/R 调查 H1） | 中 |
| `L70` | 行尾判定用 `q[32]`（包内标志），一旦源侧 `sx` 错位，`active` 的收工点错位 | 行尾多/少 2 像素 | 中 |
| `L60` | 启动门槛 `available>=GROUPS`，但 `GROUPS` 按 `SOURCE_WIDTH/4` 固定；若摄像头实际宽度 ≠1920（例如 720p 模式），**永远攒不满** → `d_de` 全无（静默黑屏） | 换分辨率必须改参数 | 事实 |
| `L52` `fault` | `fault` 同时驱动 `active` 的 kill 与 `d_de` 的门控，**没有滞回** | 抖动 | 低 |

**文档偏差**：ARCHITECTURE 未提"整行入队"这个 1 行延迟与停顿行为，直接说"gearbox 跨到 148.5 MHz"，会让人误以为是无延迟的流式转换。

### 3. `rtl/debayer/debayer_top_2to1.v`（152 行）

**职责与契约**：debayer 顶层 = `rgb_gain_v1` → `line_buffer`（2 行 RAM）→ `raw_to_rgb`，输出 48 位 = 2 像素 ×(B,G,R)。位置：gearbox 之后、`style_vga_crop` 之前，**采集域 148.5 MHz**。

**端口**

| 端口 | 方向 | 位宽 | 语义 |
|---|---|---|---|
| `in_pclk` / `in_rstn` | in | 1 | `vid_clk_dvi2` / 异步复位低 |
| `raw_vs_i` | in | 1 | `capture_vs`（gearbox 的 `d_vs`） |
| `raw_hs_i` / `raw_de_i` / `raw_valid_i` | in | 1 | **顶层三者全接 `capture_de`**（`top.v:816-818`）⇒ hs/valid 在本工程里没有独立信息 |
| `raw_datax4_i` | in | **16** | 2×RAW8：`[7:0]`=偶列、`[15:8]`=奇列（名字里的 `x4` 是历史遗留，**实际只有 2 像素**） |
| `r_gain/g_gain/b_gain` | in | **16** | Q8.8 增益（256=1.0×） |
| `rgb_vs_o/hs_o/de_o/valid_o` | out | 1 | 与 `raw_*_i` 同相，5 拍后 |
| `rgb_bout/gout/rout` | out | 16 | **每根 16 位 = 该通道的 2 个像素**（`[15:8]`=奇列，`[7:0]`=偶列） |

**内部结构**
```
in → [rgb_gain_v1 1 拍] → [line_buffer 2 拍 / 2 行] → [raw_to_rgb 2 拍数据] → 48b
```
* `L1-28` 端口；`L2-5` 参数 `RAW_GREEN_FIRST` 默认 `CFG_DEBAYER_DEBAYER_TOP_2TO1_V_PARAMETER_RAW_GREEN_FIRST = 1'b1`。

### 4. `rtl/debayer/rgb_gain_v1.v`（106 行）★ G/R 调查核心

**职责与契约**：对 Bayer RAW 做**逐像素单次** Q8.8 增益 + 255 饱和，同时产生行奇偶标记。位置：debayer 最前级（**行缓冲之前**，因此增益先于去马赛克，对后续所有插值生效）。

**端口**

| 端口 | 方向 | 位宽 | 语义 |
|---|---|---|---|
| `i_pclk / i_arstn` | in | 1 | 148.5 MHz |
| `i_hs / i_vs / i_de / i_valid` | in | 1 | 本工程全部 = `capture_de` / `capture_vs` |
| `i_data` | in | 16 | 2×RAW8（`[15:8]`=奇列、`[7:0]`=偶列） |
| `gain_r/gain_g/gain_b` | in | **16** | Q8.8（`CFG_..._V_RANGE_2/3/4 = Q_WIDTH-1:0 = 15:0`） |
| `o_data` | out | 16 | 同上格式，1 拍后 |
| `o_raw_row_odd` | out | 1 | `r_line_cnt`（**不随 `o_data` 延迟**，标注的是 `i_data` 所属行） |

**相位表（本报告的判据，务必以此为准）**

| `GREEN_FIRST` | `r_line_cnt` | `mul_high`（奇列） | `mul_low`（偶列） | 物理含义 |
|---|---|---|---|---|
| 0（板用，BGGR） | 0（偶行） | `pix_high×gain_g` | `pix_low×gain_b` | `B G` ✓ |
| 0 | 1（奇行） | `pix_high×gain_r` | `pix_low×gain_g` | `G R` ✓ |
| 1（旧 GRBG） | 0 | `×gain_b` | `×gain_g` | `G B` |
| 1 | 1 | `×gain_g` | `×gain_r` | `R G` |

**逐行要点**
* `L1-28` 端口/参数：`P_DEPTH=8`、`Q_WIDTH=16`、`GREEN_FIRST` 默认 `1'b1`。
* `L30-38` `r_line_cnt` 声明（1 bit）与 `o_raw_row_odd` 直连。**注释明确"不随 `o_data` 延迟"**，说明作者知道下游可能需要原始行标记（但顶层没用）。
* `L41-54` hs/de/vs/valid 各打 1 拍（`r_*_1P`）——**只给行计数器用，不参与数据通路**。
* `L57-65` 行计数器：`r_vs_1P && !i_vs`（VS 下降沿）清零；`r_valid_1P && r_de_1P && !i_de`（行尾后一拍）翻转 ⇒ 行内稳定。
* `L67-68` 字节拆分：`pix_high = i_data[15:8]`、`pix_low = i_data[7:0]`。
* `L74-89` 增益多路选择：`if(!GREEN_FIRST)` 一支是**后加的 BGGR 支持**；`else if(r_line_cnt)` / `else` 是**厂商原版 GRBG**。
* `L92-93` 饱和：`out_high = (|mul_high[23:16]) ? 255 : mul_high[15:8]`。
  * 位宽验证：`pix(8) × gain(16) = 24 位` ✓；`mul[23:16]` 非零 ⇔ `pix×gain ≥ 65536` ⇔ 结果 ≥256 → 夹到 255 ✓；否则取 `[15:8]` = **`>>8` 截断（无舍入）**。
  * 等价写法：`out = min(255, (pix×gain)>>8)`。
* `L95` `w_data_filtered = {out_high, out_low}`。
* `L97-104` 输出寄存 1 拍（`o_data<=w_data_filtered`，`o_de/o_valid/o_vs/o_hs` 同拍）——**数据与同步信号严格同拍**，无偏斜 ✓。

**定点运算总表**

| 算式 | 位宽 | 舍入 | 饱和 |
|---|---|---|---|
| `mul = pix × gain` | 8×16 → 24 | 无 | 无（24 位足够） |
| `out = mul>>8` | 24→16（取 [15:8]） | **截断（向下）**，最大 -1 LSB | `|mul[23:16]` → 255 |
| `w_data = {out_high,out_low}` | 16 | —— | —— |

**风险与疑点**
| 位置 | 疑点 | 现象 | 置信度 |
|---|---|---|---|
| `L92-93` | 饱和阈值由增益决定：`gain=520` → RAW `v≥126` 即饱和；`gain=290` → `v≥226` 才饱和 | **R/B 比 G 早 100 个码值饱和** → σ_R、σ_B 被削、σ_G 不动（G/R σ 比被抬高）。这是 1.95 的**最佳定量解释** | 高（算式事实） |
| `L92-93` | 无舍入（`>>8` 截断），每通道独立截断 | 单通道 -0.5 LSB 偏置，颜色最大 1 LSB 偏差；对 σ 无实质影响 | 事实 |
| `L57-65` | 行计数依赖 `r_valid_1P && r_de_1P`，而本工程 `valid=de`；若将来把 `i_valid` 接成"有像素但 de 不连续"的信号，行计数会**不再翻转** ⇒ 增益通道整体错行 | 整帧偏色 | 低（当前无害） |
| `L74-89` | `always @(*)` 里对**当前** `i_data` 用**当前** `r_line_cnt`，而 `r_line_cnt` 在行尾后一拍才翻转 ⇒ 行内稳定 ✓。但若上游某行只有 1 拍 DE（例如 gearbox 行首多一个包），翻转点会落在有效数据内 ⇒ **半行错相位** | 半行条纹 | 中 |
| `L79-88` | `GREEN_FIRST=1` 分支的注释与 `L6` 的注释**自相矛盾**（`L6` 说 1=even G/B，`L80` 注释写 "奇数行 high=Gr(gain_g) low=R(gain_r)"，两者其实一致，但 `L86` 又写 "偶数行 high=B(gain_b) low=Gb(gain_g)" 与 `L6` 的 "even G/B" 顺序相反） | 纯注释问题，易误导后续维护 | 事实（注释） |

**文档偏差**：ARCHITECTURE_FULL:105 的"`gain_g` 在奇偶行都被使用，而 R/B 各只用一次 ⇒ 可能造成通道增益不对称"——**该推理不成立**（见 G/R 专节），建议在汇总里更正。

### 5. `rtl/debayer/line_buffer.v`（167 行）

* `L4-6` 参数：`P_DEPTH=8`（实例覆盖）、`PW=P_DEPTH*2=16`、`X_CNT_WIDTH=10`（实例覆盖）。
* `L29-30` `HOR/VER_SYNC_POLARITY` 均为 `"POSITIVE"`（`defines.v`），`L58-78` 的 generate 只用于复位值，本设计下 `c_ina_vs_por=c_ina_hs_por=0`。

| 位置 | 疑点 | 置信度 |
|---|---|---|
| `L148` | bank 翻转条件是"行尾后 2 拍且当拍 `i_de=0`"。若两行背靠背（无水平消隐），`r_de_1P=0 && r_de_2P=1` 仍会在**新行第 1 拍**成立 → 新行首像素被写进**刚被读的 bank**，同时地址被清 0 ⇒ 首像素丢失/错位 | 低-中（真实 CSI 有消隐，当前不触发） |
| `L152` | `r_addr1` 只在 `i_valid` 时自增；若某行长度 >1024 字（>2048 px），地址回卷**覆盖本行自己** ⇒ 图像右半撕裂。1920 下安全，**换 2560 宽摄像头会静默坏** | 事实 |

**文档偏差**：ARCHITECTURE 未记录行缓冲深度/抽头语义；`o_x`、`raw_row_odd_o` 等悬空输出也未记录。

|---|---|---|---|

### 8. `rtl/style/style_vga_crop.sv`（48 行，链路衔接）

**职责**：从 1920×1080 取**中央 1280×960**，再 2×2 平均降到 **640×480**，输出 32 位像素。

**端口**：`clk,rst_n,i_vs,i_de,i_rgb[47:0]`；`valid,sof,eof,pixel[31:0],fault,completed_frames[31:0]`。
**逐行要点**
* `L10` `X0=(1920−1280)/4=160`（**pair 单位**，= 320 像素）、`Y0=(1080−960)/2=60` ⇒ 裁剪窗 x∈[320,1600)、y∈[60,1020) ✓ 居中。
* `L15-18` `pair_sum[c*9+:9] = i_rgb[c*8+:8] + i_rgb[24+c*8+:8]` ⇒ c=0: `[7:0]+[31:24]`（=r0+r1）、c=1: `[15:8]+[39:32]`（g0+g1）、c=2: `[23:16]+[47:40]`（b0+b1）⇒ **R 在低字节**、通道不混 ✓（这正是"R 在低字节"的独立佐证）。
* `L11,21-24` 行缓冲 `line[0:639]`（27 位/项）存偶行，奇行时取回 ⇒ 2 行平均。
* `L30-32` 只在 `odd_row` 且 `inside_crop` 时 `v1` 有效 ⇒ 每 2 输入行出 1 输出行、每 2 输入像素出 1 输出像素 ✓ 640×480。
* `L36-37` `total = previous + current + 2; pixel[..] = total[9:2]` ⇒ **4 点平均带 +2 舍入**（round-half-up）✓。注意 `total` 是 10 位，`previous[current]` 是 9 位，最大 510+510+2 = 1022 ✓ 不溢出。
* `L41` VS 下降沿复位 `pair_x/y` 并 `started<=1`。
* `L43` 行结束时 `pair_x==SOURCE_WIDTH/2-1`（=959）回卷、`y` 递增到 1079 后归 0。

**风险与疑点**
| 位置 | 疑点 | 置信度 |
|---|---|---|
| `L19` | `inside_crop` 里 `pair_x>=X0` 与 `pair_x<X0+WIDTH`，宽度 640 **pair** = 1280 px ✓；但 `y` 上限是 `Y0+HEIGHT*2` = 60+960 ✓ 一致 | 事实（核对无误） |
| `L22` | 偶行写 `line[]`，奇行读——**必须先写后读**。若某帧第一行就是奇行（`y` 从 Y0=60 起，偶数 ✓）安全；若 Y0 变奇数则首行读到上一帧残留 | 低 |
| `L30-32` | `fault` 一旦置位（本模块没有内部置位源，只有输入 `fault`——端口里它是 output）实际恒 0 | 事实 |

**文档偏差**：ARCHITECTURE_FULL 说"像素格式 XBGR，R 在 bit[23:16]"，但 `style_vga_crop` 写出的 32 位是 **`[7:0]=R, [15:8]=G, [23:16]=B, [31:24]=0`**（R 在**低**字节）。两者矛盾，需 rowpipe 侧（其它任务）确认 DDR 打包时是否又做了一次字节序调整。**统计 AE/AWB 的 `capture_frame_stats.sv:92-93` 按 `[7:0]=R` 解包**，与本模块一致 ⇒ 更可能是文档写错。

### 9. `rtl/isp/luma_color_suppress.v`（51 行，显示域 74.25 MHz）

**职责与契约**：显示前的"亮绿抑制 / 暗红抑制"——高光处压绿（去荧光灯绿偏）、暗部压红（去暗部红噪），蓝色不动。位置：`display_pixel` 之后、`luma_tone_map` 之前，**帧缓冲之后** ⇒ 只影响 HDMI 输出。

**端口**

| 端口 | 方向 | 位宽 | 语义 |
|---|---|---|---|
| `clk / rst_n` | in | 1 | `hdmi_tx_slow_clk` 74.25 MHz / `display_reset_n` |
| `i_enable` | in | 1 | `video_display_tone[0]` |
| `i_high_green` / `i_dark_red` | in | 8 / 8 | `video_display_tone[15:8]` / `[23:16]`（板上=32/32） |
| `i_vs/i_hs/i_de` | in | 1 | `ch0_vs/hs/de`（帧缓冲输出，1 px/拍） |

* `L36-40` 参数在 **VS 期间**锁存，强度夹到 **128**。
* `L45-46` `green_cut=high_weight×S_h`、`red_cut=dark_weight×S_d`（16 位，最大 32256/32640 ✓）。
* `L23-24` `factor = 256 − cut[15:8]` ⇒ `cut[15:8]≤127` ⇒ **factor∈[129,256]**，最多压 ~50% ✓。
* `L25-26` `product = v×factor`（8×9=17 位，最大 65280，bit16 恒 0 ✓ 不溢出）。
* `L47` `o_r=red_product[15:8]`、`o_g=green_product[15:8]`、**`o_b=b2`（蓝不动）**；`L48` 同步走 `sync2` ⇒ **3 级流水，数据/同步同拍** ✓。

| 位置 | 疑点 | 置信度 |
|---|---|---|
| `L47` | `product[15:8]` 无饱和，靠 `factor≤256` 保证不溢出；若有人把强度上限从 128 改大（`cut[15:8]` 会 >256 → 因子变负 → 9 位减法回卷成巨大值） | 中（结构性脆弱） |

| `L45-46` | 抑制是**幂等非线性**（乘因子），不修改 B ⇒ 会改变 R/G/B 比例（**故意去色**），也会轻微降低 G/R 的 σ | 事实 |

**文档偏差**：ARCHITECTURE_FULL:221 提到"strength 32→0 时右半 σ 从 9.9 升到 12.3"，方向正确（抑制会压 σ），但那是**显示侧**测量，与 DDR 里的 1.95 无关。

### 10. `rtl/isp/luma_tone_map.v`（48 行）★ lift 数学

**职责与契约**：显示域的"提亮曲线"（gain 型，非加法），按像素亮度查表得到增益，**用最亮通道的 headroom 夹取**以保持 RGB 比例（不产生色偏）。位置：`luma_color_suppress` 之后、DVI encoder 之前。

**端口**：`clk,rst_n,i_enable`；`i_strength[7:0]`；`i_vs/i_hs/i_de`；`i_r/i_g/i_b[7:0]`；`o_r/o_g/o_b[7:0]` + `o_vs/o_hs/o_de`。
**参数**：`HIGHLIGHT_SAFE`（模块默认 `CFG_ISP_LUMA_TONE_MAP_V_PARAMETER_HIGHLIGHT_SAFE=0`，但**实例覆盖为 1**：`top.v:901` + `CFG_TI60F225_OOB_TOP_V_INST_LIFT_ADJUSTMENT_HIGHLIGHT_SAFE 1'b1`）⇒ **板用 `lift_safe_cap_lookup`**。

**逐行要点 / 定点算式**
* `L13` `include "lift_tables.vh"`（三张 256 项函数表）。
* `L16-17` `weighted_y = R+2G+B`（10 位）；`luminance = weighted_y[9:2]` = `(R+2G+B)>>2` ✓（与 Lead 给的公式一致）。
* `L18-19` `maximum = max(R,G,B)`（逐级比较）。
* `L39` `extra1 <= lift_extra_lookup(luminance)`（**9 位**）；`cap1 <= lift_safe_cap_lookup(maximum)`（**10 位**）。
* `L41` `lift2 <= enabled ? extra1×strength : 0`（**17 位**；最大 256×128 = 32768 ✓）。
* `L25` `requested = 10'd256 + {1'b0, lift2[15:7]}` ⇒ `256 + ((extra×S)>>7)`（10 位，最大 512 ✓ 不溢出）。
* `L43` `factor3 <= requested > cap2 ? cap2 : requested` ⇒ `factor = min(256+((extra·S)>>7), cap)`。
* `L26-28` `product = v3 × factor3`（8×10 = 18 位，**`reg [17:0]`**）。
* `L44` `o_r <= red_product[15:8]` ⇒ **`>>8` 截断，取低 16 位的高 8 位**。
  * ⚠️ 这一步**没有饱和逻辑**：若 `v×factor ≥ 65536`，bit17..16 被丢弃 ⇒ **回卷**。安全性完全由 cap 表保证：
* `L37` 参数在 VS 期间锁存；`strength = min(i_strength,128)`。
* **流水线**：`r1`(1) → `r2`(2) → `r3`(3) → 输出(4)，`cap1`(1) → `cap2`(2) → `factor3`(3) → 乘法(3)，`lift2`(2) → `requested`(2)；`sync1/2/3` 同步 ↔ `o_*` 在第 4 拍 ⇒ **4 级，数据/同步严格同拍** ✓。

**风险与疑点**
| 位置 | 疑点 | 置信度 |
|---|---|---|
| `L44` | **无饱和**，`product[15:8]` 依赖 cap 表兜底。已验证现表 `max(v×factor)=65280`（余量 255/65536≈0.4%），**一旦重新生成表或把 `HIGHLIGHT_SAFE` 改成 0 且表被改小，就会静默回卷成黑/白块** | 高（结构性风险） |
| `L25`+`L43` | `requested` 上限 512（=2.0×），但 `cap ≤512` ⇒ 实际最大增益 **2.0×**，不会出现"strength=128 溢出到 >256 因子导致失控"——**该担心不成立**，但也说明 **strength=128 时暗部增益硬顶在 2.0×** | 事实 |
| `L39` | `lift_extra` 在 code 0..16 恒 0（曲线不动 ≤16），但 **17→32 单调上升到 256**，之后下降 ⇒ 曲线**非单调**：亮度 24 的像素比亮度 32 的像素得到更低增益 | 事实（有意，但会在暗部产生"提亮峰值"） |

**文档偏差**：ARCHITECTURE 只说"lift 是增益型"，未记录 `HIGHLIGHT_SAFE=1` 用的是 safe 表、也没记录"无饱和、靠 LUT 兜底"这个约束。

### 11. `rtl/isp/lift_tables.vh`（794 行，3 张 256 项表）

**结构**（`L1-2` 注释：`Generated by tools/generate_lift_tables.py; do not edit`）：

| 函数 | 行范围 | 返回位宽 | 索引 | 值域 | 形态 |
|---|---|---|---|---|---|
| `lift_extra_lookup` | `L3-266` | `[8:0]`（9 位） | `code[7:0]` | **0..256** | code≤16 恒 0；**峰值 256 @ code 32**；之后单调降到 254 处的 0 |
| `lift_cap_lookup` | `L267-530` | `[9:0]` | `code` | **256..512** | code≤~112 恒 512；之后单调降到 255 处的 256 |
| `lift_safe_cap_lookup` | `L531-794` | `[9:0]` | `code` | **256..512** | 同形但更早下压：code≥240 已降到 256 |

**抽样（每 16 点）**
```
extra: 0=0 16=0 32=256 48=235 64=224 80=192 96=171 112=142 128=120 144=100
       160=84 176=67 192=54 208=40 224=28 240=12 248=6 254=0 255=0
cap:   0..112=512 128=510 144=453 160=408 176=370 192=340 208=313 224=291 240=272 255=256
```

**全量验证（脚本 dump 全部 256 项）**

## G/R σ 异常调查（重点）

### 问题陈述
板上 `0x05800000`（风格帧缓冲，**显示链路之前**）实测行 240 全 640 像素：`σ_R=23.0、σ_G=44.9、σ_B=26.1` ⇒ **G/R = 1.95、G/B = 1.72**；模型侧同口径 `G/R = 1.06`。

### 1) 先排除测量口径（事实）
* 该缓冲是 **rowpipe 网络 L11 输出**，不是源帧。源帧在 `0x05000000`。所以 1.95 里混了"网络权重 × 输入通道统计"两层，**不能直接归因到 debayer**。
* 测量是**单行内** 640 像素的 σ ⇒ **任何逐行（奇偶行）效应都被排除**：偶/奇行增益不同只会造成**行间**差异，不会抬高**行内** σ。
* `luma_color_suppress`/`luma_tone_map`/`ae_frame_stats` 全在 **74.25 MHz 显示域、帧缓冲之后** ⇒ **不可能**影响 `0x05800000`。文献里"lift 把 σ 从 9.9 压到 12.3"是**显示侧**测量，与本题无关。

### 2) 文档假设的判定：**不成立**
文档说"`gain_g` 在奇偶行都用、R/B 各一次 ⇒ 通道增益不对称"。逐行核对（`rgb_gain_v1.v:74-89`）后：

| 物理位置（BGGR） | 本行 `r_line_cnt` | 实际乘的增益 | 次数 |
|---|---|---|---|
| 偶行 偶列（B） | 0 | `gain_b` | 1 |
| 偶行 奇列（G） | 0 | `gain_g` | 1 |
| 奇行 偶列（G） | 1 | `gain_g` | 1 |
| 奇行 奇列（R） | 1 | `gain_r` | 1 |

* **每个物理像素恰好乘一次**，且乘的是它自己的通道增益。
* `gain_g` 出现两次 = 绿像素在 Bayer 里本来就有两倍数量（这是 Bayer 的定义），**不是**"G 被乘了两次"。R/B 各出现一次同理。
* 因此**该假设不能解释 1.95**（置信度：高，代码事实）。

### 3) debayer 结构能解释什么：**恰好能解释 1.06**
对每个输出行，四个 Bayer 位置的插值核不同 ⇒ 各通道的"平滑比例"不同。设输入为不相关的高频内容（每像素独立），单点值 σ=s：

| 通道 | 单点占比 | 2 点平均(σ=s/√2) | 4 点平均(σ=s/2) | α = σ_ch/σ_s |
|---|---|---|---|---|
| **G** | 50% | 0 | 50% | √(0.5 + 0.5/4) = **0.7906** |
| **R** | 25% | 50% | 25% | √(0.25 + 0.5/2 + 0.25/4) = **0.7500** |
| **B** | 25% | 50% | 25% | √(0.25 + 0.5/2 + 0.25/4) = **0.7500** |

⇒ **σ_G/σ_R = σ_G/σ_B = 0.7906/0.75 = 1.054**。
这与模型侧 **1.06** 吻合到 1% —— 说明 **模型 1.06 就是这颗双线性核的固有签名**，不是巧合（模型侧大概率忠实复刻了 RTL 的核）。

**关键界限**：α 只取决于"平均的点数分布"，与场景强相关的内容只会让 α 向 1 收敛（相关性 ρ→1 时所有 α→1）。**因此该比值被限制在 [1.000, 1.054] 区间，结构上永远到不了 1.95。**
（`style_vga_crop` 的 2×2 平均对三通道一视同仁，再乘 0.5，不改变比值。）

⇒ **结论：debayer/rgb_gain 的"结构"能解释 1.06，不能解释 1.95。置信度：高（解析 + 代码双证）。**

### 4) 那 1.95 最可能是什么：**AWB 增益 + 255 硬截断**
把链路写成线性模型（源帧 R/B 未截断时）：
```
σ_G/σ_R = (α_G/α_R) × (gain_g/gain_r) × (σ_Graw/σ_Rraw)
        = 1.054 × (290/520) × 1  = 0.59      ← 与模型 1.06 同量级差一个增益比
```
即：**若三通道 RAW 的 σ 相近（中性场景），硬件出来的 G/R 应该 ≈0.59（G 更小）**，而实测是 **1.95（G 更大）**。要翻过来，只有"非线性/截断"能提供 ~3.3 倍的通道差。

**截断数字（精确）**：`out = min(255, (v·gain)>>8)`
* `gain_r = gain_b = 520` ⇒ `v ≥ ceil(255·256/520) = 126` **就饱和到 255**
* `gain_g = 290` ⇒ `v ≥ ceil(255·256/290) = 226` 才饱和

⇒ **R/B 比 G 早 100 个码值进入饱和**。AE 若把 G 均值压到 100~140（典型目标），R/B 会有一大块像素常年贴 255，**σ_R、σ_B 被压扁、σ_G 不受影响**，G/R 自然被抬高。
**这个预测的形状与实测完全一致**：R、B 恰好是**同一档增益（520）**的两个通道，实测它们的 σ 也恰好**同量级且都低**（23.0 / 26.1），而 G（290，唯一不同档）σ 高 1.8 倍。
**另一条独立证据**：`520/290 = 1.793`，而 `1.95/1.06 = 1.84` —— 差 3%，在 σ 的测量噪声与"截断程度未知"内可以认为吻合。

### 5) 备选假设与"能/不能"判定

| # | 假设 | 能否解释 1.95 | 定量预测 | 判定依据 | 置信度 |
|---|---|---|---|---|---|
| **H2** | **R/B 因 520 增益 + 255 硬截断被压 σ** | **能** | `σ_G ≫ σ_R ≈ σ_B`，且 R/B 均值贴 255、直方图在 255 堆峰 | 算式精确；与实测形状一致；R/B 同为 520 档 | **★★★ 中高** |
| H1 | 通道/相位旋转（列相位翻转、CSI 四像素组逆序、VS 多/少一行） | 能 | σ_G 因**混入不同均值的人群**被抬高，且图像明显偏色/棋盘；`capture_frame_stats.sv:76-80` 的 AWB 解码证明"low=偶列、偶行=BG"这一约定被两处独立使用 | 若相位反了，`rgb_gain` 与 `raw_to_rgb` 会**同时**错位（两者共用 GREEN_FIRST），**不会产生相对反转** ⇒ 反而打不开 1.79 的差 | ★ 低 |
| H3 | 固件把 520/290 写错槽位（R↔G 交换） | 能 | 三个通道均值会呈现 290/520 关系；`σ_B/σ_G` 应 =1.0（B 与 G 同增益），实测 0.58 ⇒ **不符** | 数值不符 | ★ 低 |
| H4 | 模型与板上输入不是同一场景/同一源帧 | 能（非 RTL 缺陷） | 两条链的 `σ_raw` 分布不同 ⇒ 任何比值都可能 | 无法从 RTL 判定 | ★★ 中 |
| H5 | 文档假设（`gain_g` 用两次） | **不能** | —— | §2 相位表 | 已排除 |

### 6) 结论一句话
> **debayer 结构能解释模型侧的 1.06（解析值 1.054），但结构上不可能产生 1.95；最可能的硬件机制是 R/B=520（2.03×）增益叠加 `rgb_gain_v1.v:92-93` 的 255 硬截断把 R/B 的 σ 压扁了 1.8 倍，置信度中高。文档"gain_g 用两次"的假设应撤回。**

### 7) 要验证该怎么测（不需要改 RTL）
**① 板上判决性实验（最便宜，优先做）——读源帧 `0x05000000`**

* 若三通道均值出现 290/520 的关系 ⇒ H3。
* 顺带读 `0x05000000` 的四相位：取偶数行偶数像素（应=B）、偶行奇像素（=G）、奇行偶像素（=G）、奇行奇像素（=R），检查是否真的满足"两个 G 位置数值接近"—— 这直接验证 Bayer 相位，1 次读回即可。

**② 对照实验（改固件，不改 RTL）**：把 R/B 增益降到 256、G 也 256（全 1.0×），重测 σ_G/σ_R。
* 期望：σ_G/σ_R 回到 1.05 左右 ⇒ 坐实"增益+截断"；若仍是 1.9 ⇒ 说明在 debayer 之后/网络里。

**③ 仿真 tb 方案（静态可写，不要跑 Efinity）**：`tests/` 下新建 `tb_debayer_phase.v`
1. **四色相位 tb**：构造 4×4 BGGR 合成 RAW，令 B=10、G=40、R=90（常数），跑 `debayer_top_2to1`（`RAW_GREEN_FIRST=0`、增益全 256）。断言输出每像素 `(R,G,B)`：B 位置 = (avg 90, avg 40, 10)、G 位置 = (avg 90, 40, avg 10)、R 位置 = (90, avg 40, avg 10)。**这条能一次性证明增益/通道没有互换**。

## tone / lift 数学专题（含 strength 0..128 全量行为）

### 1) 两个模块的完整数据流（都在 74.25 MHz 显示域，1 px/拍）
```
display_pixel → [luma_color_suppress 3 级] → [luma_tone_map 4 级] → DVI encoder
                    ↑ i_enable/tone[23:0]        ↑ i_enable/lift[15:8]
```

### 2) `luma_tone_map` 全式（`L16-44`）
```
Y     = (R + 2G + B) >> 2                     // 10 位加，8 位结果，无舍入
extra = lift_extra[Y]                          // 9 位，0..256，峰值 @Y=32
cap   = lift_safe_cap[max(R,G,B)]              // 10 位，256..512
lift2 = enable ? extra × strength : 0          // 17 位
req   = 256 + (lift2 >> 7)                     // = 256 + ((extra×S)>>7)，10 位，≤512
fac   = min(req, cap)                          // 10 位
out_c = (c × fac) >> 8                         // 8×10=18 位，取 [15:8]，无饱和
```

| 0..16 | 0 | 256 (1.00×) | 256 (1.00×) | 256 | 256 | 512 | 曲线恒等 |
| 17 | 31 | 256 | 263 (1.03×) | 271 | 287 (1.12×) | 512 | req |
| 24 | 171 | 256 | 298 (1.16×) | 341 | 427 (1.67×) | 512 | req |
| **32** | **256** | 256 | **320 (1.25×)** | 384 | **512 (2.00×)** | 512 | req（顶到上限） |
| 48 | 235 | 256 | 314 (1.23×) | 373 | 491 (1.92×) | 512 | req |
| 64 | 224 | 256 | 312 (1.22×) | 368 | 480 (1.88×) | 512 | req |

**回答任务里的三个具体问题**
* **"`requested = 256 + lift2[15:7]` 在 strength=128 时是否溢出到 >256 的因子？"**
  → **是，且是有意设计**：`req` 最大 = `256 + 256 = 512`（=2.00×），但**算术上不溢出**（10 位，最大 1023），且 `extra≤256` 保证 `req≤512`。落地增益 = `min(req,cap)`，亮部被 cap 锁在 1.00×，所以**不会失控**。
* **"`product[15:8]` 会不会回卷？"** → 只要 cap 表满足 `v×cap(v) ≤ 65535` 就不回卷。全量验证：`lift_safe_cap`（板用）max = **65280**（v=255，余量 255），`lift_cap` max = **65280**（v=128）。**成立但余量仅 0.39%**，属结构性风险。
* **"luminance=(R+2G+B)/4 的实现对不对？"** → 对：`{2'b0,r}+{1'b0,g,1'b0}+{2'b0,b}` 是 10 位精确和（≤1020），`[9:2]` 是 `>>2`（截断，非四舍五入）。与 `luma_color_suppress`、`ae_frame_stats`、`capture_frame_stats` 三处**完全同一写法**，全工程口径一致 ✓。

### 3) 对 σ 的影响（为什么它不能解释 1.95）
* lift 是**逐像素的局部增益** `out ≈ (fac/256)·in`，因此 `σ_out ≈ (fac/256)·σ_in` —— **对所有通道乘同一个 fac**（fac 只由 Y 决定），所以 **不改变通道间 σ 比**，只会整体压/放 σ。
* 实测"关 lift 后 σ 9.9→12.3"正是这个整体效应（fac<1 时压 σ，因为转换曲线斜率 <1）。
* **定量**：S=32 时 fac ∈ [256, 320] ⇒ 斜率 1.00~1.25；由于 `>>2` 截断与 fac 的逐像素变化，**同一亮区的 σ 会被放大最多 1.25 倍**（暗部）或不变（亮部）。
* 结论：**tone/lift 不可能产生 G/R=1.95 的通道差**（且它位于帧缓冲之后，对 `0x05800000` 无影响）。

### 4) `luma_color_suppress` 全式（对照用）
```
Y = (R+2G+B)>>2
gh = (Y>192) ? (Y-192)*4 : 0              // 0..252
dr = (Y<64)  ? min(255, (64-Y)*4) : 0     // 0..255
green_factor = 256 - ((gh*S_h)>>8)        // S_h≤128 ⇒ ≥130  ⇒ 绿最多 ×0.508
red_factor   = 256 - ((dr*S_d)>>8)        // S_d≤128 ⇒ ≥129  ⇒ 红最多 ×0.504
out_g = (g*green_factor)>>8 ; out_r = (r*red_factor)>>8 ; out_b = b
```
* **只看 Y**，不看具体颜色 ⇒ 在暗部**无条件压红**、在高光**无条件压绿**，是一个"亮度分段去色"。
* S=32（板）时：`Y=255` ⇒ 绿 ×0.879；`Y=0` ⇒ 红 ×0.879；`Y∈[64,192]` ⇒ 恒等。
* 该操作**会降低 R（暗部）/G（高光）的 σ**，且是逐像素幂等映射 ⇒ 在显示侧制造"通道间 σ 差"，但**位置在帧缓冲之后**。

## 给 Lead 的 5 条要点

1. **文档问题 3 的 debayer 假设应当撤回**：`rgb_gain_v1` 对 BGGR 是逐像素单次增益（偶行 B/G，奇行 G/R），`gain_g` 出现两次只因为绿像素数量是两倍，不是重复乘。相位表在 §4，可直接引用。
2. **1.95 的最佳解释是"R/B=520 的 2.03× 增益 + 255 硬截断"**（不是相位、不是 debayer 结构）：R/B 在 RAW≥126 就饱和、G 要到 226，被压的是 R/B 的 σ；`520/290=1.79` 与 `1.95/1.06=1.84` 只差 3%，且 R、B（同一增益档）实测 σ 同量级且都低，形状完全吻合。**一次读回 `0x05000000` 的三通道 mean/σ/饱和占比即可定案**（判决性实验，不需要改 RTL）。
3. **1.06 是双线性核的固有签名（解析值 1.054）**：G=50% 单点/50% 四点平均，R=B=25%单点/50%两点/25%四点 ⇒ σ_G/σ_R≈1.054，且对任意场景被限制在 [1.00,1.054]，**结构上不可能到 1.95**。这条把"模型侧 1.06"从疑问变成证据（模型确实复刻了 RTL 核）。
4. **前端有两个必须记录的结构性脆弱点**：① `raw_to_rgb.v:352` 用 `r_y_cnt[0]` 选行公式，而公式作用在中心行 `n-1` 上——±1 行的差错就整体翻相（`LEGACY=1` 的幻影行、gearbox 的"s_valid=de&hs"是唯一支撑）；② `luma_tone_map.v:44` 的 `product[15:8]` **无饱和**，安全性只靠 `lift_safe_cap` 满足 `v×cap≤65535`（实测 max 65280，余量 0.39%），改曲线脚本而不改 RTL 会静默回卷。
5. **几处与 ARCHITECTURE_FULL 的出入**（源在文档错，均未改文档）：① 增益寄存器在 `video_apb_ctrl.sv:52` 不是 47；② 板上 `display_meter` 是 `FULL_FRAME_MEAN=1`（**全帧**均值），不是中央 50%；③ `0x05000000` 的 32 位像素按 `style_vga_crop.sv:36-37` 是 `[7:0]=R`（R 在**低**字节），与文档"R 在 bit[23:16]"矛盾；④ `capture_frame_stats.sv` 被 include 但**从未实例化**（死代码，真正在跑的是 `video_apb_ctrl` 内部累加器）；⑤ 文件行数与任务书略有出入（实测 152/422/106/167/145/228 行），内容不受影响。
