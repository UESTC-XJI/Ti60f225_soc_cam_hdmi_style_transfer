## 结论先行（5 条）

1. **Q1：不会漏过"有害"的帧，但确实失去了"丢帧"这层网 —— 而且在修好的位段下这道网本来就已经是死的。**
   把 `hot>samples` 提前钳到 0，效果是把这个异常帧从「`:125-126` 丢弃」改成「接受、但 hot=0 ⇒ goal=128」。
   由于 `camera_3a.c:125` 仍校验 `y_sum ≤ samples*255`、`samples>0`、`flags`、`cfg`，**AE 真正依赖的 mean 仍然被完整校验**，
   被钳掉的只有 hot 一个字段 ⇒ 该帧的 AE 决策退化成"和改动前完全一样"。**结论：可以放心，风险等级低。**
   补充：位段修好之后 `hot ≤ n` 在结构上恒成立（`:155-156` 两者同拍分别 +2 / +(0..2)），所以 `:125` 的
   `v.hot>v.samples` 这一支**在任何正常帧上都不可能触发**，它现在只是防御性死码。

2. **⚠️ 需要纠正你的注释：旧位段不是"只有真值的一半"，而是"低段加倍、高段回绕、50%–85% 直接丢帧"。**
   `st_hot` 只有 21 位（`video_apb_ctrl.sv:56`），打包在 `ae_rx[73:53]`（`:164`），旧代码取 `[73:52]` = **22 位塞 21 位**，
   保留的是 `{hot[19:0], n[20]}` ⇒ `st_hot_old = n[20] + 2·(hot mod 2^20)`，而满幅帧 `n = 1,228,800 ≥ 2^20` ⇒ **`n[20]=1`**。
   于是：`hot < 614,400` 时读值 ≈ **2×hot+1**（放大，不是缩小）；`hot ≥ 1,048,576` 时 MSB 被丢 ⇒ 回绕成小值（非单调）。
   **`camera_3a.c:117-118` 那句"读出的 hot 只有真值的一半"会把后续排障带偏，建议改写。**

3. **Q2：有实打实的压暗风险，而且比"−19%"更严重 —— 因为 hot 是"增益后"统计的，几乎恒在触发区。**
   证据链：`rgb_gain_v1.v:95-96` 是 **Q8.8（`>>8` + 8 bit 饱和到 255）**；`debayer_top_2to1.v:41-65` 把它放在**数据链第一级**；
   AE 统计读的 `rgb_data` 是它的下游输出 ⇒ **阈值 232 是对"增益后"码值判的**。
   当前增益 520/290/520 ⇒ R/B 各 **×2.031**、G ×1.133 ⇒ R/B 通道只要**原始码值 ≈114** 就满足"≥232"，到 **≈126 就饱和 255**。
   也就是说 `hot` 实际上主要在数"R/B 被色彩校准裁顶的像素"，而不是场景高光 ⇒ 一旦接入 goal，
   **goal 会在几乎所有室内场景被钉在下限 104（−18.75% ≈ −0.30 EV），不分场景永久压暗。**
   **建议：先不要用现有的 knee=10‰/cap=24；至少改成 knee≈100‰ + cap 16（floor 112），并按 `mean` 做门控。**

4. **Q4：`:109` 的 `G_ACTIVE==256` vs `:175` 的 `290` 一字未动，仍是潜伏 bug；最小修法是 1 个 token。**
   现状态：AWB 依旧全死（`camera_awb.c:13-14` 守卫 + RTL 0x180-0x1A0 硬连 0，本轮未变）⇒ 该分支不可达。
   最小修法：`camera_3a.c:109` 的 `256` → `STYLE_G_GAIN`；推荐再对称化出一个 `expected_g`。

5. **Q5：最快回退就是 `camera_3a.c:119` 这一行 —— 而且不用重烧 bit。**
   把 `if(v.hot>v.samples) v.hot=0;` 改回 `v.hot=0;` 即完全恢复改动前行为（RTL 的位段修复对丢弃 hot 的固件完全惰性）。
   **注意配对**：新固件 + 旧 bit 时，`:119` 的钳制**救不了**"低段加倍"（只在 `hot>samples` 时触发，即 ≥50% 区间），
   会出现"提前压暗"，见下表 B 列。

## 1. 会不会漏过 `:125` 本该拦掉的异常帧？

**改动前后对照（`camera_3a.c:113-126`）**

| | 改动前 | 改动后 |
|---|---|---|
| `:119` | （无） | `if(v.hot>v.samples) v.hot=0;` |
| `:125` | `…||v.hot>v.samples||…` → **return（丢帧）** | 该子条件**必然为假**（hot 已被钳） → 继续执行 |
| 帧的去向 | 丢弃：`last_seq/last_frame` 已在 `:124` 更新，但 `last_stats_time` 不更新 ⇒ 1 s 后 `:122` 判 `NO_STATS` | 接受：AE 正常更新，`high_permille` 用钳后的 0 ⇒ goal=128 |

**判断（分三层看）**

1. **能漏过去的是什么？** 只有 `hot` 一个字段异常（`hot>samples` 意味着"热像素比采样像素还多"，物理不可能）。
   `y_sum`、`samples`、`flags`、`cfg` 是**各自独立**的位段（`ae_rx[31:0]`/`[52:32]`/`[0d0]`/`[137:106]`），
   位段错位不会同时污染它们；它们仍被 `:125-126` 完整校验（`y_sum ≤ samples*255` 能兜住粗差）。
2. **漏过去之后会干什么？** `hot=0` ⇒ `high_permille=0`（`:139`）⇒ `goal=128`（`:140`）⇒
   该帧的 AE 行为**等价于改动前的固件**。也就是说泄漏的后果是"这一帧退回旧行为"，不是"把错误放大"。
3. **丢掉的那层网值不值钱？** 丢帧的代价是 `last_stats_time` 冻结，1 s 后 `NO_STATS`；
   如果位段再次出错（比如烧回旧 bit），**接受帧显然比冻结 AE 更划算**。

**结论**：安全。但建议把"钳制发生"变成可见事件，否则位段问题会静默：

```c
if(v.hot>v.samples) { v.hot=0; s->errors++; }   /* camera_3a.c:119，一行，让 UART 的 err 字段能看见 */
```

顺带两点（都不影响当前行为）：
- `:125` 的 `v.hot>v.samples` 现在是**不可达死码**（结构上 `hot ≤ n`）。留着无妨（防御），但别指望它再拦东西。
- 钳制放在 `:120-123` 的"seq 未变就 return"**之前**，同一帧的重复调用会重复钳（幂等，无害）；若想更贴语义可移到 `:124` 之后。

## 2. `camera_ae_goal()` 的真实行为、压暗风险与建议下限

**实际曲线**（`camera_ae.c:5-8`）：`reduction = high>10 ? (high-10)/4 : 0`；`goal = 128 - min(reduction,24)`

| `high_permille` | goal | 说明 |
|---|---|---|
| 0–13 | 128 | 死区（`(high-10)/4` 取整后仍为 0） |
| 14 | 127 | 开始生效 |
| 50 | 118 | −7.8% |
| 100 | 106 | −17.2% ≈ floor |
| **≥106** | **104** | **下限，−18.75%（−0.30 EV）** |

你对"106‰ 触底"的计算**正确**。

**风险评估：有，而且我判断它在板上会"几乎常开"。**

1. **触发门槛极低。** 106‰ = 10.6% 的像素"热"。按 `rgb_gain_v1.v` 的 Q8.8 语义 + 当前 520/290/520 增益，
   R/B 在**原始码值 114** 就计入热、126 就饱和 —— 室内带白墙/浅色桌面的画面很容易超过 10%。
   而 `ARCHITECTURE_FULL.md` §八 #5 已记录"亮场景 23% 像素饱和" ⇒ 那种场景 goal 稳在 104。
2. **压暗幅度与"暗部细节"：** AE 是闭环，`camera_ae_target()`（`camera_ae.c:15`）用 `current*goal/mean` 比例逼近，
   所以 mean 会收敛到 104 而不是 128 ⇒ **整幅线性亮度 ×0.8125**，暗部码值同比例下降（如 40→32），
   在 8 bit + 已存在的"右半同色 70.9%"问题下，暗部更容易被并进平坦区。
3. **与色彩校准强耦合（这是最麻烦的一点）。** hot 统计在增益之后 ⇒ 增益↑ ⇒ hot↑ ⇒ goal↓ ⇒ AE↑曝光，
   形成一个 **"色彩校准 → 高光计数 → 曝光目标"的隐性反馈**。以后任何人重标 R/B 增益都会连带改变 AE 行为。
4. **注释与实现不符。** `camera_ae.c:2-4` 写着"Highlights soften the metering goal **rather than unconditionally darkening an already dark scene**"，
   但实现里**只看 high、完全不看 mean** —— 暗场景同样会被压。这个承诺目前没被实现。

**建议（按改动量从小到大）**

| 方案 | 改哪 | 具体值 | 效果 |
|---|---|---|---|
| **A. 最小且推荐**（固件，两行常量） | `camera_ae.c:6-7` | `high>100`（knee 10‰→100‰）、`reduction>16u`（cap 24→16） | goal ∈ [112,128]，−12.5% 上限，只在 >10% 热时启动 |
| **B. 兑现注释里的承诺**（固件，1 行门控） | `camera_ae.c:5` 增加 mean 入参或 `camera_3a.c:140` 前判断 | `if(s->mean>=110) goal=…; else goal=128;` | 暗场景（mean<110）**一律不压暗**，保住暗部 |
| **C. 真正修根因**（RTL，需重新综合） | `video_apb_ctrl.sv:142-143` | 把阈值按增益归一：`>= (232*gain)>>8`，或在 `rgb_gain_v1` 增益前产生 hot 位 | hot 变成"场景高光"而非"R/B 裁顶"，与校准解耦 |
| **D. 加滞回/限速**（固件，约 8 行） | `camera_3a.c:139-140` | 进：连续 2 帧 `high>knee`；出：`high<knee/2`；每次 goal 变化 ≤2 | 避免 hot 抖动导致 goal 抽动（见下） |

**推荐组合：A + B**（纯固件，不动 RTL，风险可控）；如果视觉上还想更亮，再考虑 C。

**关于"加滞后"必须注意一个坑**：`camera_ae_goal()` 每次 AE 更新会被**调用两次** ——
`camera_3a.c:140` 一次、`camera_ae.c:12`（`camera_ae_target()` 内部）又一次，且都传同一个 `high`。
**如果把状态机写进 `camera_ae_goal()`，它会被双步进**（一次更新推进两格）。
正确做法：状态放在 `camera_3a_service()`（`:139-140`，那里已经有 `s->ae_goal` 字段），
并把 goal 作为参数传进 `camera_ae_target()`（`camera_ae.c:11` 签名加一个 `goal` 形参），
避免两处独立重算导致"守门用的是 A、决策用的是 B"。

## 3. `st_hot` 的语义与单位是否和 `samples` 一致？

**先给结论：累加侧完全正确，"少累加一半"不成立；问题只在读侧位段（你已修）。**

| 检查项 | 代码 | 结论 |
|---|---|---|
| 语义 | `video_apb_ctrl.sv:142-143` `ae_hot0/1 = R≥232 \|\| G≥232 \|\| B≥232` | ✅ 就是"任一通道 ≥232"的像素 |
| 每拍累加 | `:156` `ae_hot <= ae_hot + hot0 + hot1` | ✅ 每拍最多 +2，**两个像素都算** |
| 与 n 同步 | `:155` `ae_n <= ae_n + 21'd2` | ✅ 同一拍、同样 +2 ⇒ **单位一致（都是"像素"）** |
| 同一裁剪窗口 | `:147` `ae_in_crop`，`:153-157` 三个累加都在 `if(ae_in_crop)` 内 | ✅ hot 与 n/y 同一窗口 |
| 窗口尺寸 | `ae_x` 0..959（960 对 = 1920 px，`:158-161`）× 行 60..1019（960 行）× 2 px | ✅ = 1,228,800，与 `samples` 及 `:146` 注释吻合 |
| 字段宽度 | `reg [20:0] ae_n, ae_hot`（`:134`）；`0x0e8 = {11'd0, st_hot}`（`:106`） | ✅ 1,228,800 < 2^21，不溢出 |

**但"语义"还有一个必须提醒的口径问题**：阈值 232 判的是 **Q8.8 增益后、饱和到 255** 的码值
（`rgb_gain_v1.v:95-96` `out = (pix*gain)>>8`，饱和 `2^8-1`；`debayer_top_2to1.v:41-65` 该级在数据链最前），
而增益是 520/290/520 ⇒ R/B ×2.031、G ×1.133。
所以：`hot` ≈ "**R 或 B 被色彩增益推到 232 以上的像素数**"，不是"过曝像素数"。
**它和 `mean`（同样增益后）是自洽的**，但与"传感器真实高光"不是一回事 —— 这条直接支撑 Q2 的压暗风险。

**另外建议加一道 1 行防御**（`:139`）：`high_permille` 没有上限钳制，
旧位段下可以算出 >1000‰（实测最大 1707‰），虽然 `camera_ae_goal` 有 `min(…,24)` 兜底、不会溢出，
但日志与诊断会看到怪值：`if(high_permille>1000) high_permille=1000;`

## 4. `:109` 潜伏 bug 的现状与最小修法

**现状（逐行确认）**

| 行 | 代码 | 状态 |
|---|---|---|
| `camera_3a.c:109` | `…||video_read(VIDEO_G_ACTIVE)!=256)` | ❌ 仍写死 256 |

`status=6 / enabled=0 / errors++`，3A 永久停摆（`:110` 之后没有任何重新使能路径，除相机重连）。

**最小修法（择一）**

```c

```

（`camera_3a_t` 加一个 `expected_g` 字段，`camera_3a.h:9` 同排）

③ 最省事但会丢校验：直接删掉 G 这一项（G 恒定 290，`video_ctrl.c:9` 已保证非零，apply 失败还有 R/B 能暴露）——
