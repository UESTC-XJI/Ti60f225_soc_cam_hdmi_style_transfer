# CI/CO 16→8 功能等价性仿真验证（iverilog A/B）

> 日期：2026-10-27 19:20–19:55　｜　**纯离板**：未碰板子/OpenOCD/串口，未跑任何位流构建，未改 `software/firmware/`
> 目标：回答三个问题 —— (1) CI=CO=8 与 16 输出是否逐位相同？(2) 若不同，第一处差异在哪层/第几个 beat？(3) 根因是位宽截断还是别的？
> 结论：**(1) 逐位相同（两级证据）；(2)(3) 不适用 —— 没有差异**；并给出"为什么必然相同"的 `file:line` 结构性论证 + 一个必须写进前提的安全条件。

---

## 一、三问三答（结论先行）

| 问题 | 答案 | 证据 |
|---|---|---|
| **1. CI=CO=8 与 16 输出逐位相同吗？** | **是，逐位相同** | ① 整网 A/B：768 个输出 beat 的 SHA256 **完全相同**，且 12 层逐层"写 hash + 写计数"全部一致；② 单元级：4 个断言全 PASS，含负向对照 |
| **2. 若不同，从哪层/第几 beat 开始？** | **不适用（无差异）** | 逐层 hash 表见 §4；负向对照证明比对**有**判别力（只翻 1 个 bit 就能测出 188/384 像素不同） |
| **3. 根因是位宽截断吗？** | **截断是无害的，而且被证明"高通道字节对输出完全无影响"** | 单元测试 PASS-1（高 64 位换图案，输出 0 差异）+ PASS-2（截断后 0 差异）；结构性原因见 §6 的 6 条 `file:line` |

**推荐结论：CI/CO 16→8 可以安全落地**，但有**一个前提条件**必须同时钉住（§7.1）：**所有层的 `cfg_ci ≤ 8` 且 `cfg_cout ≤ 8`**。当前 12 层全部满足（最大 ci=8/cout=8），所以安全；若将来出现 ci=16 的层，CI=8 会**静默丢掉通道 8..15**。

### 2.2 `DESCS_TINY` 的换算规则（为什么这样缩放仍然"是同一套逻辑"）

只换 `win/hout/wout/ng`，**`ci/cout/res/resu/xorin/s2/up/srcb/dstb/idb/idxor/srcf/dstf/idf` 全部逐层照抄**。
缩放后仍必须满足设计自身的几何约束（否则测的就不是同一个数据通路）：

| 约束 | 出处 | tiny 满足情况 |
|---|---|---|
| `s2=0`：`wout==win`、`win%16==0`、`ng=win/16` | `rowpipe_layer.v` 窗口/PIX 关系 | L0/L3~L8/L11：64/32 宽 ✓ |
| `s2=1`：`win==2*wout`、`ng=wout/8` | 引擎 `S_RPAD` 空跑一整行 | L1: 64/32/4 ✓；L2: 32/16/2 ✓ |
| `up=1`：`hout%2==0`（每源行用两次）、`win` 偶 | `srcW=win/2`、`iy[0]` 换源行 | L9: 32/24/2 ✓；L10: 64/48/4 ✓ |
| 层消费列数 == `(s2?4:1)*hout*wout` | `rowpipe_engine.v` 的 `in_total_r` | 12 层全部对得上（实测每层都正常收尾） |

结果帧从 640×480 变成 **64×48**（768 个 16 B beat）。

## 三、方法与速度（含"为什么只有 1.7k 拍/秒"）

### 3.1 加速账：靠"缩小几何"，不是靠工具

| 方案 | 一帧拍数 | 预估耗时 @1.7k 拍/s |
|---|---|---|
| 全尺寸 640×480（Lead 的 TB） | **4,925,xxx**（≈4.9M，`TRACK3_COMPUTE_RESTRUCTURE.md` 的 33.2 ms@148.5 MHz） | **≈48 分钟/次** |
| **TB_TINY=1（64×48）** | **92,773**（实测） | **55.7 s/次** |
| 加速比 | **53×** | A/B 两次 ≈ **111 s** + 编译 1.2 s |

**实测（本机，Windows，iverilog 14.0 devel）：**
```
ci16: wall=55.7s  92773 cycles  ≈1666 cycles/s
ci8 : wall=55.7s  92773 cycles  ≈1666 cycles/s
编译：ci16.vvp 0.6s / ci8.vvp 0.6s，各 5.68 MB bytecode
单元测试：3096 拍 / 2.1 s
```

### 3.2 关于"为什么只有 1~2k 拍/秒"（Lead 点名要查）

我测了几种可能，结论是**这只是 iverilog 解释器在这个规模上的固有速度，不是 TB 写错了**：

| 怀疑 | 实测/结论 |
|---|---|
| `src_beat()` 组合函数每 beat 都在算 | 已改成按**地址**生成（每次 16 次迭代），量级 ≈10⁵ 次迭代 → **<0.2 s**，不是瓶颈 |
| `rmem`/`wmem` 大数组 | `$readmemh` 903 行、`rmem` 768 行，都是**一次性**，<0.1 s |
| `efx_dsp48` 行为模型 | 65 个实例本身不重（每拍 2 次乘），但它把 DSP 内部四级寄存都展开成事件 → 每拍额外 ~260 个事件 |
| **主因** | 设计规模：**~25k FF + 34.7k LUT4 + 3 块大 RAM 数组（`lb` 163,840 bit / `id_rb` / 读流 FIFO）**。iverilog 是字节码解释器，每个时钟沿要把所有寄存器/组合锥重新求值一次 ⇒ 约 **0.6 ms/拍** |
| 有没有提速开关 | `vvp -h` 只有 `-n/-q/-s/-i/-M`，**没有任何优化级别**（iverilog 不是优化型编译器）。`-g2012` 只影响语法 |

**⇒ 唯一的加速杠杆就是"少跑拍数"**，也就是 TB_TINY 这条路（53×）。这也解释并印证了 Lead 观察到的现象：L0 是 825k 拍 × 0.6 ms ≈ **8 分钟**，所以"5 分钟没跑完"完全正常。

### 3.3 激励的确定性（A/B 可比的前提）

所有读数据都是**地址的纯函数**（`pat_beat()`），源帧、中间 bank 全部如此；权重来自 `wgt.hex`（903 beat，redsky v5）。⇒ 两次运行的输入流逐位相同，唯一变量就是 CI/CO。

> ⚠ 这里有个**必须改的地方**（相对于 Lead 原来的 TB）：原 TB 对"非源帧地址"一律返回 0，而**残差恒等支 `i_id` 正是从中间 bank 读的** ⇒ 如果中间 bank 全 0，那么 128 位截断到 64 位**测不出来**（0 截断还是 0）。所以我把所有地址都改成确定性模式数据。这是本次改动里对"检验有效性"最关键的一处。

## 五、单元级截断证明（回答"最大风险点"）

整网 A/B 只能说明"相同"，不能说明"**为什么**相同、以及**什么条件下**会不同"。所以补了一个锁步单元测试 `tests/tb_layer_ci_trunc.v`：

**四个 DUT 共享同一套激励**（`s_vld/grp_vld/skip_vld/cfg_*` 完全共享），配置成**残差层**（`cfg_res=1, resu=1, ci=8, cout=8, win=32, ng=2, hout=12`）：

| DUT | 配置 | `s_col/i_id` 高 64 位 | 用途 |
|---|---|---|---|
| A | CI=16/CO=16 | `0xA5A5...` | 基准 |
| B | CI=16/CO=16 | `0x5A5A...`（**只有高通道不同**） | 断言"高通道字节无影响" |
| C | **CI=8/CO=8**（端口 64 位） | 被剪掉 | 断言"截断等价" |
| D | CI=16/CO=16，**通道 0 的 LSB 取反** | 同 A | **负向对照**：必须与 A 不同 |

**实测结果**（`_sim/unit.vvp`，3,096 拍 / 2.1 s）：
```
消费列数=434 (期望 434)  像素数 A/B/C = 384/384/384 (期望 384)
s_ack 三路不一致拍数 = 0
输出非退化：与 capA[0] 不同的像素 = 383 / 384（0 说明测试无效）
----------------------------------------------------------
PASS-1: 高通道字节(A=0xA5.. / B=0x5A..)对输出**无影响**
PASS-2: CI/CO 16→8 截断后输出**逐位相同**
PASS-0(负向对照): 只翻通道0的LSB ⇒ A vs D 有 188 个像素不同（比对有判别力）
PASS-3: s_ack 消费节奏三路一致（共 434 列）
样本：A[0]=...f817201b280516f4  A[1]=...ef060dfb2d0926f4  A[2]=...ec0ef611282019f4
```

三条读法：
1. **PASS-1 是核心**：它直接测出"通道 ≥8 的字节**根本不参与**输出计算"。既然高 64 位无论怎么变都不影响输出，把它剪掉（CI=8）当然等价。
2. **PASS-0 是"检验的有效性"**：同一条通路只翻通道 0 的 1 个 bit 就有 188/384 像素变化 ⇒ 这个比对**非常灵敏**，PASS-1/PASS-2 的"0 差异"不是"测不出来"。
3. **PASS-3**：`s_ack` 是层的消费节奏（上游靠它推进指针），三路完全一致 ⇒ 宽度变化没有影响流水推进（若这里不一致，问题会比数据错更严重）。

## 六、为什么必然等价（结构性论证，`file:line`）

1. **taps 只取 ci < cfg_ci**：`rowpipe_layer.v:671` `step_go = (st==S_STEP) && (ci_cnt<cfg_ci)`。12 层 `cfg_ci ≤ 8`（最大 ci=8），所以 ci=8..15 的 `(ci,ky,kx)` 步**永远不会发出**。
2. **窗口只采低 8 个通道**：`rowpipe_layer.v:524` `sb_c = tile ? q_c[8*(gi+CIX)+:8] : q_c[8*gi+:8]`，`gi < CIW = 8` ⇒ `q_*` 只有低 64 位进窗口，高 64 位**从不被采样**。这就是 PASS-1 的 RTL 依据。
3. **输出高半区本来就是 0**：`rowpipe_layer.v:341` `rq_col_full = half_d5 ? {rq_q, CO_EXTRA*8 个 0} : {CO_EXTRA*8 个 0, rq_q}`，而 `npass2` 被硬钉成 0（`rowpipe_layer.v:254`）⇒ `half_d5 ≡ 0`。所以 CO=16 时高 64 位恒 0，CO=8 时高 64 位不存在（引擎侧 128 位线自动补 0）——**两种情形下引擎看到的 128 位字完全一样**。
4. **恒等支只用前 8 个通道**：`rowpipe_layer.v:969` `rq_id_full[32*gri] = (gri<cfg_ci) ? ... : 0`（`gri<CO`），而消费端 `rq_id_arr[32*gh] = rq_id_full[32*(rq_sel_d*CO_ARR+gh)]`（`gh<CO_ARR=8`，`rq_sel_d≡0`）⇒ 只有通道 0..7 会被用。CO=8 时生成 8 个（值相同），CO=16 时生成 16 个但只用前 8 个。
5. **量化器与 CO 无关**：`rowpipe_layer.v:922` `requant #(.COUT(CO_ARR), .CO_STORE(CO_FILL), ...)`，`CO_ARR=8` / `CO_FILL=8`（`rowpipe_layer.v:200/203`）是**独立 localparam**，不从 `CO` 推导 ⇒ `CO` 无论 16 还是 8，requant 的阵列宽度/M 存储/饱和逻辑**一个字节都不变**。
6. **`lb`/`OW`/`rq_id_r*` 只是变窄**：它们存的是同一批被选中的字节，宽度随端口走，语义不变（`lb` 的环回逻辑只依赖 `D=1280` 与 `cfg_win`，与 CI 无关）。

**⇒ 一句话**：这个网络里 `CI*8` 的**高 64 位是结构性死数据**（`cfg_ci ≤ 8` 决定），所以把它剪掉不改变任何可观测行为。

## 七、落地建议

### 7.1 安全条件（**必须写死，否则会像 #1 那样复发**）

> `CI=8` **只在所有层 `cfg_ci ≤ 8` 且 `cfg_cout ≤ 8` 时成立**。

- 当前 12 层：`ci ∈ {3,4,8}`、`cout ∈ {3,4,8}` ⇒ 成立 ✓。
- 若将来加一层 `ci=16`：`CI=8` 会**静默丢掉通道 8..15**（窗口只存 8 通道、`step_go` 只到 ci=7、恒等支只生成 8 个），**不报错、不告警**，只表现为画质变差。这与 10-26 那条"L11 隐式 ReLU"是同一类失败模式（配置错 → 静默降级）。
- 建议至少做一条机器检查（三选一）：
  (a) `rowpipe_engine.v` 里加 `synthesis translate_off` 的断言：`cfg_ci > 8` 时 `$display` 告警；
  (b) 导出 blob 的脚本断言 12 层 `ci ≤ 8`；
  (c) 固件自检里读描述符并检查（最贴近上板路径）。

### 7.2 具体改法（一行 + 一个参数保持不动）

```
rtl/accel_rowpipe/rowpipe_engine.v:147
- rowpipe_layer #(.CI(16), .CIW(8), .PIX(16), .CO(16), .COUT(16)) u_layer (
+ rowpipe_layer #(.CI(8),  .CIW(8), .PIX(16), .CO(8),  .COUT(8))  u_layer (
```
**`CIW` 必须保持 8**（它是"窗口通道数"= 本网络最大 ci），改成 8 正好等于 `CI`，于是 `TILED=(CIW<CI)=0` ⇒ tile 全套死逻辑被剪掉（这本身也是收益之一，见 `01_rowpipe_layer.md` 要点 2 / `16_area_budget_track1.md` §四）。

### 7.3 预期收益（引自既有审计，本次未重测）

- `lb` 163,840 → 81,920 bit：**省 8 个 10 kbit RAM 块**；`id_rb` 43,264 → 21,632：**省 2 块** ⇒ RAM 244 → **约 234/256**；
- `rq_id_r1..5` 640→320 FF、输出 FIFO 槽 258→194 bit、tile 全套逻辑消失 ⇒ **约 −1.3k XLR**；
- 时序：`lb`/FIFO 变窄，扇出与布线资源同时减少，方向有利（**未实测**，需构建后看 `timing.rpt`）。

### 7.4 构建后自查（3 分钟）

1. `hier_util.rpt`：`u_layer` 的 MEM 列应从 **86** 降到 **≈76**；`u_rd0/u_rd1` 不变（读流与 CI 无关）。
2. `map.rpt`：`EFX_RAM10` 总数应从 **240** 降到 **≈230**。
3. 时序：`vid_clk_dvi2` 域 setup slack 应 ≥ 现状（CI 缩小不会引入新路径）。
4. 上板：先跑 L11 输出直方图，确认 σ/均值与改动前同量级（数据通路若被搞坏，σ 会明显变化）。

## 八、局限与诚实边界

| 项 | 状态 |

## 文末更正（2026-10-27 对抗性复核后）

复核发现本报告有两处说法不准确，已在上文就地修正，另外补充说明：

1. **`s_col` 不在被验证之列**。它是 `[PIX*8-1:0]`=128 位，**与 CI 无关**，
   `defparam` 改 CI 不会改它 ⇒ A/B 两边 `s_col` 都是 128，这个改动没被测到。
   它的真实语义是"一个像素的 `CI` 个通道字节"（`rowpipe_layer.v:502` `q_c <= s_col`，
   `:524` `q_c[8*gi +: 8]` 按通道取），不是"PIX 个像素"。

2. **`o_col` 高位是 z 不是 0**。`rowpipe_engine.v:131` 的 `wire [127:0] o_col` 连到
   `rowpipe_layer` 的 `[CO*8-1:0]=[63:0]` 输出端口时，**未驱动的 [127:64] = z**（端口连接
   不像赋值那样补 0）。当前无害：`rowpipe_engine.v:243` `out_word` 在 `cout<=8` 时直通
   `o_col`，再被 `rowpipe_ddr_banks` 的紧凑打包只取低位字节 ⇒ **z 到不了 DDR**。
   但由此 **"所有层 cout<=8" 变成一个必须钉住的前提**（与 CI<=8 同等重要）。

3. **本次综合没有覆盖的两处**：
   - `relu_dis`（P0 修复）是新接的信号，A/B 两边都有它 ⇒ 测不出它的正确性。
   - `CO=8` 时 `CO_EXTRA=0` 会让 `rowpipe_layer.v:342` 出现零宽复制 `{0{1'b0}}`。
     **Efinity 2026.1 接受这个写法**（本次构建 map/interface/pnr/pgm 全 PASS，面积
     XLR 59,776 / RAM 202），但它不是 Verilog-2001 的标准写法，换工具链时需注意。
