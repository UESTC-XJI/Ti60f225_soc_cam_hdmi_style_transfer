## 三、v14a_safe 的修正尝试（已失败）

### 改了什么

| 项 | 值 |
|---|---|
| 权重差异 | **119 / 3,612 词（3.3%）** |
| 首个差异位置 | 词 **[124]** |
| **变化模式** | `0x61524d48` → `0x30a926a4`（**正好除 2**） |
| **性质** | **量化乘数右移 1 位** |
| 代码差异 | 413 B（100 个区间，散落） |

### 改动思路是合理的

**把量化乘数减半**，理论上能把激活值压回 INT8 的 ±127 范围，抑制溢出。

参考我们之前在 ch16 上的教训：

| 模型 | 激活 maxima | 量化 PSNR | 结果 |
|---|---|---|---|
| ch12 | 1.1–16.2 | 35.7 dB | ✅ 健康 |
| ukiyoe v15 (ch24) | 1.4–23.4 | 34.4 dB | ✅ 健康 |
| **ch16（错误配方）** | **3.2–954.3** | 9.2 dB | ❌ 发散 |

**健康模型的激活最大值应 < 25。**

### 但结果依然全零

| 区域 | t1 快照 | t2 快照 | 判定 |
|---|---|---|---|
| **源帧** `0x05000000` | `0060706a...` | `00414242...` | ✅ **在变** |
| **slot0** `0x05800000` | `00818181...` | `00818181...` | ❌ **全零** |
| **slot1** `0x05940000` | `00818181...` | `00818181...` | ❌ **全零** |

**结论：量化范围不是根本原因。**

## 四、DDR 内存实测（决定性证据）

通过 OpenOCD 直接读 DDR，对比两个时刻：

| 区域 | 地址 | 状态 |
|---|---|---|
| **源帧** | `0x05000000` | ✅ **有变化**（摄像头采集正常） |
| **slot0 风格帧** | `0x05800000` | ❌ **全 `0x00818181`** |
| **slot1 风格帧** | `0x05940000` | ❌ **全 `0x00818181`** |
| **权重区** | `0x06F00000` | ✅ **正确加载**（与固件头文件逐字一致） |

`0x00818181` = `0x010101` XOR `0x808080` —— 显示端把**零值**转换后的结果。

**结论**：ink 权重下，rowpipe 网络没有向 DDR 写出任何有效结果。

## 五、为什么 starry 正常而 ink 不正常

### 已排除的原因

| 可能原因 | 排除依据 |
|---|---|
| 权重加载失败 | ✅ DDR `0x06F00000` 内容与头文件逐字一致 |
| 地址配置错误 | ✅ source=`0x05000000`、result=`0x05800000` 两侧一致 |
| 摄像头采集故障 | ✅ 源帧在变化 |
| 推理未执行 | ✅ NN 计数 17/s 递增 |
| **RTL 写通路损坏** | ✅ **同一 bit、同一通路，starry 正常工作** |
| 固件编译错误 | ✅ 四版固件 text 段大小一致（28,256 B） |
| **量化范围溢出** | ❌ **v14a_safe 把乘数减半后仍全零** |

### 剩余的最可能解释

**ink 权重与这块 bit 的 RTL 结构参数不匹配。**

| 可能的不匹配项 | 说明 |
|---|---|
| **层描述符（拓扑）** | rowpipe 硬编码 12 层 ci/co/k，ink 可能是不同的拓扑 |
| **通道数** | ink 可能对应别的通道配置（如 24 通道 vs 8 通道） |
| **权重 blob 布局** | `[w:ci*9][b:4][M:8][q:1]` 的分段边界可能对不上 |

**starry 那套权重是专门为这个 12 层 rowpipe 架构导出的**，而 ink 的可能是从别的架构移植过来的 —— 结构不匹配导致网络读完权重后输出的全是零。

## 六、权重版本溯源

### v13 / v14a / v14a_safe 的关系（实测确认）

| 项 | v13 | v14a | v14a_safe |
|---|---|---|---|
| 文件大小 | 28,268 B | 28,268 B | 28,268 B |
| **代码（.text）** | 与 v14a **完全相同** | — | 与 v14a 差 413 B |
| **字符串表** | 与 v14a **完全相同**（18 条） | — | 相同 |
| 权重 XOR | `0x6efbe663` | `0x434fd8b6` | `0x20eb625b` |
| MD5 | `f78204e3...` | `eaa93892...` | `4fa6d430...` |

**三者代码基本相同，只有权重不同 —— 是同一份固件源码配不同模型。**

### v14a = 仓库原版权重

**v14a 的 XOR `0x434fd8b6` 与仓库原有 `software/firmware/rowpipe_weights.h` 完全一致。**

实测验证：用仓库原版权重重编译，产物 MD5 = `eaa9389250c1c26128c638e901eb5ef4`，**与 v14a 逐字节相同**。

### v13 是第三套权重

**v13 的 XOR `0x6efbe663` 不在仓库内任何变体里**（current / g065 / g075 / g085 都对不上）。已从 `v13.bin` 的 `0x34F8` 处提取并生成头文件。

## 八、修复建议

### 短期（立即可用）

**烧回 starry g075** —— 这是目前唯一验证可用的配置：

1. 烧 bit `outflow/ti60f225_oob.bit`（17.9fps 版）
2. 载入用 `_backup_179fps/rowpipe_weights_starry_g075.h` 编译的固件
3. 实测：MS 58 / 17.2 fps / UF 0 / 画面正常

### 中期（若必须用 ink 风格）

| 方案 | 说明 | 工作量 |
|---|---|---|
| **A. 检查 ink 模型的层描述符** | 确认 12 层 ci/co/k 与 RTL 硬编码是否一致 | 1–2 h |
| **B. 对比 ink 与 starry 的权重 blob 布局** | 逐段解析，找出结构差异 | 2–3 h |
| **C. 重新训练 ink** | 按 rowpipe 12 层全 3×3 拓扑重训 | 4–6 h + 导出 |

**方案 A 最优先** —— ink 若拓扑不同，量化怎么调都没用。

### 长期（架构层面）

**为导出加校验**：训练完成后自动检查
1. 层描述符是否匹配 RTL 硬编码的 12 层
2. 各层激活最大值是否 < 25
3. 导出后用整数模型跑一遍，确认输出非零

这样能避免"训练成功但上板无输出"的浪费。

### 关键流程

```
1. 板子重启（不断电重烧有 bug）
2. 烧 bit：_flash_new.bat
3. 启动 OpenOCD：_ocd_new.bat
4. reset halt
5. load_image "<bin>" 0x1000 bin
6. reg pc 0x1000 → resume
7. 读串口 COM11 遥测
8. ffmpeg 抓采集卡帧做数值分析
9. OpenOCD halt → mdw 读 DDR 对比
```
