# Track 3 算力优化方案（离板设计，2026-10-27）

> 结论：**算力已占 66%，RTL 效率已贴近理论下限**，唯一出路是改网络的空间结构。
> 而这里有一个几乎免费的机会：**卷积权重与分辨率无关**，所以可以把网络的"尾巴"
> 搬到低分辨率而不重训。方案 A 省 **8.53 ms（25.7%）**，输出分辨率不变。

---

## 一、先看钱花在哪（按描述符逐层算，与实测 4.925M 拍吻合）

公式：`cycles = (out_px / 16) × (ci × 9 + 16)`

| 层 | ci | cout | 输出 | cycles | ms | 占比 |
|---|---|---|---|---|---|---|
| **L10** | 8 | 4 | 640×480 | 1,689,600 | **11.38** | **34.3%** |
| **L11** | 4 | 3 | 640×480 | 998,400 | **6.72** | **20.3%** |
| **L0** | 3 | 4 | 640×480 | 825,600 | **5.56** | **16.8%** |
| L9 | 8 | 8 | 320×240 | 422,400 | 2.84 | 8.6% |
| L1 | 4 | 8 | 320×240 | 249,600 | 1.68 | 5.1% |
| L2–L8 | 8 | 8 | 160×120 | 105,600 ×7 | 0.71×7 | 2.1%×7 |
| **合计** | | | | **4,924,800** | **33.16** | 100% |

三条结论：

1. **640×480 上的三层（L0/L10/L11）吃掉 71.3%（23.66 ms）**
2. 320×240 的两层 13.6%，160×120 的七层只有 15.0%
3. 所以"加深网络"应该深在低分辨率——**160×120 加一层只要 0.71 ms，640×480 要 11.38 ms（差 16 倍）**

---

## 二、关键发现：`up` 机制已经存在，而且卷积权重与分辨率无关

`rowpipe_engine.v` 里早就有半分辨率采样：

```verilog
wire [31:0] srcW = up ? (win/2) : win;
if (up && iy[0]) src_base <= src_base + srcW;          // 每个源行读两遍
wire [19:0] src_addr = up ? (src_base + ix[19:1]) : ptr;  // 水平 2× 最近邻
```

语义是：**本层输出保持全分辨率，但输入按半分辨率采样**。当前 L10 就是这么读 L9 的
（L10 描述符 `up=1`，读 L9 的 320×240 输出，自己按 640×480 卷积）。

而 **3×3 卷积权重与分辨率完全无关**——搬一层到半分辨率，权重原样复用。
⇒ 这条优化**不需要模型侧重训、不需要换权重文件**，只改描述符几何。

---

## 三、方案 A（推荐先做）：把尾巴降到 320×240

**做法**：只需两处描述符改动。

| 层 | 现在 | 改为 | 理由 |
|---|---|---|---|
| L10 | `mk(8,4, 640,480,640,40, ..., up=1)` | `mk(8,4, 320,240,320,20, ..., up=0)` | 卷积改在 320×240 做，直接读 L9 的 320×240 输出 |
| L11 | `mk(4,3, 640,480,640,40, ..., up=0)` | `mk(4,3, 640,480,640,40, ..., up=1)` | 输出仍 640×480，但输入按半分辨率采样 L10 的 320×240 |

**为什么自洽**：L9 输出 320×240 → L10 在 320×240 卷积（up=0，顺序读）→ L11 在 640×480
卷积但把 L10 的 320×240 上采样来读（up=1）。链路宽度与地址几何完全对得上，
而且和"今天 L10 读 L9"是同一个模式。

| 指标 | 现在 | 方案 A |
|---|---|---|
| 算力 | 33.16 ms | **24.63 ms**（−8.53，−25.7%） |
| 每帧总时间 | 50 ms | **≈41 ms** |
| 帧率 | 18 fps | **≈24 fps** |
| 输出分辨率 | 640×480 | 640×480（不变） |
| 权重 | redsky v5 | **同一套，不用换** |

**代价**：L11 实际看到的是 320×240 的特征，输出的高频细节会减少（画面偏柔）。
这是唯一的取舍，且**上板一看就知道能不能接受**。

---

## 四、方案 B（A 之上再降 L0）

L0 是 640×480 上的输入卷积（3→4），占 16.8%。它读的是相机原帧。
把 L0 降到 160×120 后，L1 的输入几何要跟着从 640→160 改。

| 指标 | 方案 A | 方案 B |
|---|---|---|
| 算力 | 24.63 ms | **19.42 ms** |
| 帧时间 | ≈41 ms | **≈36 ms** |
| 帧率 | 24 fps | **≈28 fps** |
| 代价 | 尾巴变柔 | 尾巴 + **输入丢失高频**（影响更大） |

建议先做 A，看质量能不能接受，再决定 B。

---

## 五、方案 C：省下的算力用来加深度（模型侧的事）

160×120 上一层只要 **0.71 ms**，640×480 要 11.38 ms。所以 A/B 省下的 8.5~13.8 ms
如果用来加深度，可以在 160×120 加 **12~19 层**（面积允许的话）。

**但面积会先撞墙**：XLR 已 99.12%（剩 533）、RAM 244/256（剩 12 块）。
所以"加深度"的前置条件是先做 **CI/CO 16→8**（省约 10 块 RAM + 1.3k XLR）。

而 CI/CO 那件事比看起来复杂：`CI` 直接决定 `s_col`/`o_id`/`i_id` 的端口宽度
（都是 `CI*8` 位），`conv3x3_core` 里还硬写着 `.CIN(16)`，`TILED` 标志随之翻转
⇒ 是**接口级改动**，不是调参数。当前 rowpipe **零仿真覆盖**，改错会静默出错图。

## 六、落地方式（已实现为编译期开关）

`style_network_rowpipe.sv` 新增参数：

```verilog
parameter integer TAIL_LOWRES = 0,   // 0 = 现状；1 = 方案 A（L10 降到 320×240 + L11 up）
```

描述符用三元表达式按它切换。**默认 0 = 行为完全不变**（已验证：默认 0 重编出的
XLR 60,267 / bit 3,246,465 B / vid +0.472 与改动前逐项相同，即 netlist 未变）。

### ⚠ 实测：`TAIL_LOWRES=1` 现在**编不过**

| 配置 | XLR | 布线 |
|---|---|---|
| TAIL_LOWRES=0（现状） | 60,267 / 99.12% | **PASS** |
| TAIL_LOWRES=1（方案 A） | 60,147 / 98.93% | **FAIL ×2**（连试两次都挂在布线拥塞） |

关键事实：**这个改动几乎不省面积**（只差 120 XLR）——它只改描述的几何常量，
不删任何硬件。**它省的是时间（8.53 ms），不是面积。**

所以方案 A 现在被**面积卡住**，不是因为逻辑有问题，而是因为整个设计已经贴着
布线天花板（99% 附近成功与否是概率性的；而 60,147 这个 netlist 两次都没过）。

**要启用方案 A，必须先腾面积**，唯一大额来源仍是 CI/CO 16→8（约 10 块 RAM +
1.3k XLR），而那是接口级改动、需要 TB 兜底。见 §五。

### 上板验证判据（等方案 A 能编过之后）

| 判据 | 期望 |
|---|---|
| UART 的 `MS` | 50 → ≈41（算力应降 ~25%） |
| `NN` 帧率 | 18 → ≈24 |
| 画面 | 仍是正确的风格化结果，但**明显更柔** |
| `AXI` / `DROP` / `FAULT` | 保持 0 |
| DDR 导出的 σ | 可能略降（细节少了），但不应该出现平坦区 |

## 六、配套工具（离板阶段已备好）

改动 datapath 的风险是"能编过、时序也对、但出图是坏的"，且**不报任何错**。
下面两个工具就是为这件事准备的，都已经过验证。

### 6.1 `tools/build_check.py` —— 构建裁决器

**为什么需要**：Efinity 的 `pnr : PASS` 只代表"跑完了"，不代表能用。今天实测过一个
构建：`pnr : PASS`，但 `vid_clk_dvi2` setup slack = **−0.710 ns**。烧上去就是随机出错图。

```bash
python tools/build_check.py              # 检查当前 outflow/
python tools/build_check.py --build      # 先跑构建再检查
```

输出：阶段结果 / 面积（超过 99% 会警告）/ **逐时钟对最差 slack（负值红旗）** / 关注域
（`vid_clk_dvi2`、`core_clk`）/ 裁决 `USABLE | TIMING_FAIL | ROUTE_FAIL | BUILD_FAIL`，
退出码非 0 表示不可用，可直接串进脚本。

### 6.2 `tools/frame_diff.py` —— 金帧回归

**为什么需要**：rowpipe 零仿真覆盖、环境里也没有 HDL 仿真器。所以**用板子当仿真器**。

```bash
# 1) 在已知良好的构建上抓基准（场景/光照尽量保持不动）
python tools/frame_diff.py capture redsky_v5_known_good

# 2) 改完 RTL、重烧之后，抓一帧对比
python tools/frame_diff.py check redsky_v5_known_good

# 3) 事后比两个已存文件（不需要板子）
python tools/frame_diff.py --a a.bin --b b.bin
```

比对项：三通道均值/σ、B−R、平坦区占比、贴轨率、**16×16 块级相关**。
裁决 `EQUIVALENT / DIFFERENT / BROKEN`。

**已验证**：自比 → EQUIVALENT；不同增益的两帧 → DIFFERENT（均值差 2.1 > 阈值）；
**人工构造的"末层被 ReLU"坏帧 → BROKEN**（平坦区 53.7%、σ 比 0.36），诊断信息正确。

**局限（必须知道）**：摄像头输入不是冻结的（AE 会动、场景会变），所以它抓得住
**大错**（错图、通道错位、平坦区），抓不住 ±1 LSB 的细微差异。要真正逐位对拍需要
冻结输入的 TB。

### 6.3 用它来验证 CI/CO 改动的推荐流程

```
1. 当前已知良好构建  → frame_diff.py capture golden   （抓基准）
2. 改 CI/CO=8 → 构建 → build_check.py                （先确认能编、时序为正）
3. 烧板 → frame_diff.py check golden                  （再确认功能等价）
4. 三步都过 → 面积腾出来了，可以回头启用 TAIL_LOWRES=1
```
