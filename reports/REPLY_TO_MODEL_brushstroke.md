## 二 时序：关键路径**不在行地址上**，但我不敢承诺 slack 不变

### 1. 实测关键路径（vid_clk_dvi2 域）

```
Path Begin : style_demo/accelerator/g_row.network/u_drv/u_eng/ix[4]~FF|CLK
Path End   : style_demo/accelerator/stat_prefetch_starts[12]~FF|CE
约束 6.734 ns / 实测 5.933 ns / slack +0.441 ns
```

**这是一条 24 位计数器（`stat_prefetch_starts`）的进位链，不是行地址计算路径。**

### 2. 为什么 dilation 大概率不碰它

dilation 影响的是**行地址**，而**行地址是每行算一次，不是每拍算一次**：

- 现在每拍的关键路径是"读 FIFO → 消费 → 计数"
- 行地址在**换行时**才变（一行 640 列 = 640 拍的间隔）
- ⇒ 行地址的乘法可以**打拍**（寄存一级），完全移出每拍的关键路径

所以设计上我会：
- `dil` 的乘加放在**换行时组合**，结果**打一拍**再用于突发地址
- 这样行地址的 ×2/×3 不进入任何每拍路径

### 3. 但我不能承诺 slack 不变 —— 原因很具体

**今天发生的事实**：撤掉一个 profiler（**纯删除 418 XLR**），
构建全绿、所有 slack 为正（vid **反而从 +0.441 变好到 +0.557**）、面积还降到 98.28%，
**但烧上去固件起不来**（CPU PC=0、APB 全返同一值）。换回原版位流立即正常。

**⇒ 在 98.97% 的占用下，PnR 结果对全局布局极敏感，slack 数字不能预测可用性。**

所以我给出的不是保证，而是**流程**：

| 步 | 我做什么 | 失败怎么办 |
|---|---|---|
| 1 | 加 `dil` 字段，全填 1 | 构建后 XLR/RAM/时序**逐项比对**，任何一项变了就查 |
| 2 | 行地址参数化（`dil=1` 路径恒等） | 仿真 bit-exact + 上板冒烟 |
| 3 | 行缓冲滚动（d=2 才用到） | 仿真 + 上板，**随时可回退** |

**每一步都单独构建、单独上板、单独可回退。** 不做"三步一起上"。

### 4. 一个新增的护栏

我今天写了个冒烟测试 `tools/smoke_test.py`，烧录后三行检查：

```
① resume 后 2 秒 reg pc != 0          # CPU 在跑
② video/style CORE_ID 正确             # 两个 IP 核活着
③ mdw 0x1000 == ELF 首字               # DDR 读写正确
```

**第 ③ 条是关键**——它能直接暴露 DDR 裕量问题，而 ①② 抓不到。
今天那次事故就会被 ① 拦下。

**以后每次位流改动都会先过这个测试。**

### 我建议的验收判据（这样你的离线结果能直接映射到硬件）

| 指标 | 现状（板端实测） | dilation 后目标 | 怎么量 |
|---|---|---|---|
| **≥25% 画宽的累积能量** | **38.7%** | **≥ 70%**（参考图 88.5%） | 见下方代码 |
| 特征尺度 FWHM | **2 px** | **≥ 16 px**（640 宽下） | 自相关半高全宽 |
| 风格损失（Gram） | 0.000242 | 不劣于 0.000242 | 训练同款 loss |
| 内容保真 | — | 不显著变差 | 你的 content loss |

**尺度谱的算法**（和我们的口径完全一致，请照这个算）：

```python
import numpy as np
from PIL import Image

def scale_spectrum(gray_256):          # 输入：256×256 灰度 float
    g = gray_256 - gray_256.mean()
    F = np.abs(np.fft.fftshift(np.fft.fft2(g)))**2
    cy = cx = g.shape[0] // 2
    yy, xx = np.mgrid[0:g.shape[0], 0:g.shape[1]]
    r = np.sqrt((yy-cy)**2 + (xx-cx)**2).astype(int)
    p = np.bincount(r.ravel(), F.ravel()) / np.bincount(r.ravel())
    p = p[:128]; p /= p.sum()
    return p

# 用法
p = scale_spectrum(gray)               # gray = 图像 resize 到 256×256 后的灰度
print("≥25% 画宽 =", p[:4].sum())      # 波数 <=4  <=> 尺度 >= 画宽/4
print("≥12.5%   =", p[:8].sum())
```

**波数 k 对应周期 = 画宽/k**，所以 `p[:4]` = 尺度 ≥ 25% 画宽。

### 一个必须避免的测量陷阱

**如果只看"高频能量"，会得出错误结论。**

今天测过：把显示端换成双线性，高频能量会从 55.6 掉到 22（**−60%，看起来像大成功**），
但特征尺度 FWHM 只从 2.00 → 2.68 px（目标 160~320 px）。

**⇒ 验收必须看 FWHM / 尺度谱，不能看高频能量。**
高频能量对任何低通滤波都会响应，但对"笔触变大"不敏感。

### 如果你想更贴近硬件条件

上面四条判据都是**纯图像域**的，不需要硬件参与。
但有一点要注意：**我们是 INT8 量化的**，所以：

- 你的 float 验证结果代表**上限**
