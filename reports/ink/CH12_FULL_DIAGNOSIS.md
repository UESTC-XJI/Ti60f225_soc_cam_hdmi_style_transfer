# ch12 剪枝失败：全面排查结论

> 日期：2026-10-22
> 结论：**RTL 逻辑对 ch12 全部正确；失败在「输出像素与固件期望值不符」(-6)，需要定位到具体层**

---

## 一、排查过程（逐项验证）

### 1.1 通道分组逻辑 ✅

| 项 | ch12 | ch24 |
|---|---|---|
| `co_groups = ceil(co/8)` | **2** | 3 |
| `red_groups` (1×1) = `ceil(ci/12)` | **1** | 2 |
| 系数槽位需求 | **43** | 86 |
| 容量 256 槽 | ✅ 够 | ✅ 够 |

### 1.2 每行字节对齐 ✅

| 层 | 分辨率 | co | 行字节 | 16B 块 | 余数 |
|---|---|---|---|---|---|
| 0 | 320×240 | 8 | 2560 | 160 | **0** |
| 1 | 160×120 | 8 | 1280 | 80 | **0** |
| 2-18 | 160×120 | **12** | **1920** | **120** | **0** |
| 19 | 320×240 | 12 | 3840 | 240 | **0** |
| 20 | 320×240 | 8 | 2560 | 160 | **0** |
| 21 | 640×480 | 8 | 5120 | 320 | **0** |
| 22 | 640×480 | 3 | 2560 | 160 | **0** |

**全部整块对齐，无余数。**

### 1.3 写打包逻辑 ✅（我曾误判为缺陷）

```verilog
wb_next |= ({{128{1'b0}}, pack_pixel} << (wc_next[5:2]*32));
wc_next += wbpp;
```

`wc` 是**字节偏移**，`wc_next[5:2] = (wc>>2)&3`。逐像素验证：

| bpp | px0 | px1 | px2 | px3 | 结论 |
|---|---|---|---|---|---|
| 8 | 0→0 | 8→64 | 0→0 | 8→64 | ✅ |
| **12** | **0→0** | **12→96** | **8→64** | **4→32** | ✅ |
| 16 | 0→0 | 0→0 | 0→0 | 0→0 | ✅ |
| 24 | 0→0 | 8→64 | 0→0 | 8→64 | ✅ |

**bpp=12 的移位全部正确。（我最初的「必须 8 对齐」推断是错的）**

### 1.4 3×3 非 depthwise 约束 ✅

RTL 只支持 `ci==3` 的 3×3 非 dw。ch12 只有 layer 0（ci=3）符合，**无违规层**。

### 1.5 depthwise 通道边界 ✅

```verilog
activation_word[...] = depthwise ?
  (co_group*8+ac_lane<input_channels ? dw_slice[ac_lane*8+:8] : 8'b0) : ...
```

ch12 的 `co=12, co_groups=2`：第 2 组 lane 4-7 的 `co_group*8+ac_lane = 12..15 >= 12` → **正确置零**。

### 1.6 1×1 的 `pw_terms` ✅

```verilog
pw_terms = input_channels==8 ? {32'b0, pw_slice[63:0]} : pw_slice;
```

- `ci=8` → 取前 8 通道 ✅
- `ci=12` → `pw_slice` = 96 bit = 12 通道 ✅

### 1.7 norm 参数范围 ✅

| 项 | ch24 | ch12 | 位宽限制 |
|---|---|---|---|
| multiplier m | 16,389–32,739 | **10,518–32,700** | 16 bit（32767）✅ |
| bias b | −3.54e8..2.13e9 | **−5.08e8..1.98e9** | 32 bit（2.147e9）✅ |
| shift r | 17–28 | **18–28** | 8 bit ✅ |

**无溢出。**

## 二、板上实测解码（关键突破）

APB 读回 16 个寄存器（`0xf8100200`）：

| 寄存器 | 值 | 含义 | 判定 |
|---|---|---|---|
| `regs[0]` | `0x3154534E` | 版本号 | ✅ 正确（排除 -1） |
| `regs[2]` | `0x10` | `{coeff_idle,0,error_sticky,done_sticky,pending}` | coeff_idle=1, **error=0, done=0, pending=0** |
| `regs[3]` | `0x01` | irq_enable | ✅ 已使能 |
| `regs[4]/[5]` | `0x05000000`/`0x05800000` | 源/目标 | ✅ |
| `regs[6]` | `0x01E00280` | 640×480（已恢复） | ✅ |
| `regs[7]` | **`0x00007862`** | **`last_cycles = 30,818`** | ✅ **对 32×24 合理** |
| `regs[10]` | `0x0000FF17` | coefficient_index | — |
| `regs[12]` | **`0x18001800`** | `{acknowledged, issued}` = 6144/6144 | ✅ **系数装载正确** |
| `regs[13]` | `0x08D9EE20` | 148,500,000 | ✅ |

### 关键结论

**`last_cycles = 30,818` 是正常的！**

| 项 | 值 |
|---|---|
| 32×24 的 ch12 MAC | 259,200 |
| 满速（96 MAC/cycle）| 2,700 cycles |
| 实测 | **30,818 cycles** |
| 640×480 的 ch12 应 | 约 12M cycles |

**30,818 与 32×24 的小图推理量级吻合**（含行缓存/DRAM 开销）。

### 失败分支定位

| 分支 | 判据 | 实测 | 结论 |
|---|---|---|---|
| -1 版本 | `regs[0] != 0x3154534E` | 相等 | ❌ 排除 |
| -2 超时 | `(regs[2]&17) != 16` | `0x10&0x11=0x10` ✅ | ❌ 排除 |
| **-3 计数** | `regs[12] != expected\|expected<<16` | `0x18001800` ✅ 相等 | ❌ 排除 |
| -4 IRQ 超时 | `app_style_irqs` 未变 | — | ⚠️ 待定 |
| -5 status | `status & 4` | `error_sticky=0` | ❌ 排除 |
| **-6 像素不符** | `output != expected` | 唯一剩下的可能 | ✅ **最可能** |

**→ 推理正常完成、无硬件错误，失败点是输出像素与固件 `expected` 不符。**

## 三、这意味着什么

**RTL 对 ch12 的通道分组/对齐/打包全部正确**，但**实际算出的像素与 Python 整数 oracle 不一致**。

可能原因（按可能性）：

| # | 原因 | 验证方法 |
|---|---|---|
| **1** | **固件的 `expected` 与 RTL 实际使用的系数不同源** | 对比固件 expected vs ch12 export oracle |
| **2** | ch12 的量化标定导致某些层饱和，RTL 与 Python 的饱和处理不同 | 逐层中间结果对比 |
| 3 | ch12 模型的某层触发了 RTL 未覆盖的边界 | iverilog 分层仿真 |

### 关键已排除项

✅ 固件 `expected` 与 `export_ch12` 的整数 oracle **完全一致（0/768 不同）**
✅ RTL 的 `coeff.bin` 与固件 `style_weights.h` **6144/6144 匹配**

**→ 所以问题在 RTL 实际计算与 Python 整数模型的差异上。**
