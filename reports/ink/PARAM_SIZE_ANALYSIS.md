# 为什么赛题写「参数量 <500 KB」？有什么好处？

> 日期：2026-10-21
> 数据来源：**实测资源报告 + RTL 代码 + 计算**
> 结论：**500 KB 不是「宽松的锦上添花」，而是 Ti60F225 的物理上限决定的硬约束；
> 参数量大确实带来画质/鲁棒性好处，但我们 10.8 KB 的代价就是那些一直没解决的短板**

---

## 一、先看我们的实际情况（全部实测）

| 项 | 值 | 来源 |
|---|---|---|
| **参数量** | **9,201 个** | `student_v3` checkpoint 统计 |
| **INT8 payload** | **11,056 B = 10.8 KB** | `model.bin` |
| 层数 | 23 | `graph.json` |
| 系数表 | 6144 词 × 32 bit = **24 KB** | `coeff.bin` |

**我们只用了赛题限额的 2.2%。**

---

## 二、为什么是 500 KB —— 由片上存储决定

### 2.1 关键事实：我们的系数**不在**片上 block RAM

查 `style_row_core.sv:70`：

```verilog
(* syn_ramstyle="block_ram" *) reg [31:0] mem[0:255];   // 256 词 × 32 bit = 1 KB
```

**每层只驻留 256 词（1 KB）**，靠 APB 逐层流式换入：
```c
// style_driver.c:38
regs[10] = (row<<8) | word;
regs[11] = style_coefficients[row*24u + word];
```

**→ 6144 词 = 24 KB 系数，同一时刻只有 1 KB 在片上。**

### 2.2 片上 RAM 已接近饱和

| 项 | 实测 |
|---|---|
| Ti60F225 RAM 总块数 | **256** |
| **当前已用** | **237（92.58%）** |
| **剩余** | **19 块** |
| 其中 `style_demo` | **121 块（47%）** |
| └ `mac:style_mac8x12` | **112 块**（96 乘法器的流水寄存器） |

### 2.3 500 KB 参数装不下（关键推论）

| 项 | 数值 |
|---|---|
| 500 KB = 512,000 个 INT8 参数 | 4,096,000 bit |
| 若全放片上，按每块 ~10 Kbit 估算 | **需约 400 块** |
| **但总容量只有 256 块，且已用 237 块** | **装不下** |

**→ 赛题写 500 KB，实际含义是**：
**「你得把权重放 DDR 流式加载」**，而不是「必须做到 500 KB」。

### 2.4 500 KB 的真实语义

| 参照 | 参数量 |
|---|---|
| ResNet-50 | 25.6 M |
| VGG-16 | 138 M |
| Fast Neural Style（1/4 通道） | 约 50 K–200 K |
| **我们的微 CNN** | **9.2 K** |
| **赛题上限** | **500 K** |

**500 KB ≈ 500 K 参数**（INT8 1 字节/参数）。
**这是「别用几十 MB 的骨干网」的粗线，而非精确的工艺要求。**

## 三、参数量大的好处（逐条对照我们的实测短板）

### 好处 1：表达容量 → 决定画质上限

| 项 | 说明 |
|---|---|
| **理论** | 参数越多，能拟合的风格纹理越精细 |
| **我们的实测短板** | **笔触始终没做出来**（这是本项目反复确认的未解问题） |
| **根因** | 9.2K 参数 + RTL 只有 3×3/1×1 算子，**无法表现精细笔触** |
| **若参数翻 10 倍** | 可加频域/多尺度残差，笔触有机会 |

### 好处 2：鲁棒性 → 我们的过曝问题

| 项 | 说明 |
|---|---|
| **理论** | 大网络对光照/场景变化更稳 |
| **我们的实测短板** | `blown95% = 13.32%` vs 目标 `4.24%`（**9 项验收中唯一 FAIL**） |
| **根因** | 小容量下，损失函数稍有偏差就顾此失彼（v3 冻结、v5 posterization 都是这个表现） |

### 好处 3：多风格共享骨干

| 项 | 说明 |
|---|---|
| **理论** | 大网络可「共享编码器 + 小 head」，切风格只换 head |
| **我们的现状** | 需 **9 个独立模型**（浮世绘 v15、水墨 v3、黑白 v1–v6），每个 10.8 KB |
| **代价** | **切风格必须重载全部 6144 词**（无法只换 head） |

### 好处 4：训练稳定性

| 项 | 说明 |
|---|---|
| **理论** | 大网络好优化 |
| **我们的实测** | v3 训练冻结（AMP GradScaler 死循环）、v5 posterization、v6 只过 8/9 项 |
| **根因** | 9.2K 参数下，损失函数权重稍有偏差就崩 —— **小网络对超参极敏感** |

---

## 四、参数量大的**代价**（为什么不能无脑加大）

| 代价 | 我们的实测证据 |
|---|---|
| **片上存不下** | 256 块 RAM 已用 92.6% |
| **DDR 带宽** | 每帧读 1,132,523 beat = **18.1 MB**；加 500 KB 系数仅 +2.8%（可接受） |
| **AR 握手增加** | **AR 等待已是 45.9% 最大瓶颈**；每层重载系数 = 更多握手 |
| **帧率** | 当前 11 fps，**要求 15 fps** —— 参数量增大直接拖慢 |
| **切换延迟** | 赛题要求 <100 ms；系数越多加载越慢 |

**→ 这就是赛题为什么写「<500 KB」而不是「越大越好」：**
**在 Ti60F225 上，参数量与实时性是直接对立的。**

---

## 五、我们 10.8 KB 的定位

| 维度 | 评价 |
|---|---|
| **赛题限额** | ✅ **仅用 2.2%，极度轻量** |
| **实时性** | ◐ 11 fps，**仍未达 15 fps** |
| **画质** | ◐ 风格达到（暖米黄明显），**笔触/过曝是短板** |

**这是一条「极度压缩」的路线**，代价就是画质短板 —— 而这正是参数量小的必然结果。

---

## 六、结论

### 为什么是 500 KB

1. **Ti60F225 片上 RAM 只有 256 块**，且已用 92.6% —— **装不下 500 KB**
2. 所以 500 KB 的真实含义是 **「允许你用 DDR 流式加载权重」**
3. 它是**「别用 ResNet/VGG」的量级门槛**，不是精确工艺指标

### 参数量大的好处

| 好处 | 我们的实测印证 |
|---|---|
| 画质上限（笔触） | ✅ **笔触始终没解决** |
| 鲁棒性（过曝） | ✅ **blown95% 13.3% vs 目标 4.2%** |
| 多风格共享 | ✅ 需 9 个独立模型，切换要全量重载 |
| 训练稳定 | ✅ v3/v5/v6 反复失败 |

### 但代价是实时性

**我们的 10.8 KB 换来了「能塞进资源」，但输掉了「笔触与过曝」。**
**赛题 500 KB 的限值，本质是在「画质」与「Ti60F225 上的实时性」之间划一条线。**
