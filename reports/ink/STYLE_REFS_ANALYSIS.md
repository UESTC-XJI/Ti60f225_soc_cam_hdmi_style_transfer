# 风格参考图数量：对训练速度与效果的影响

> 日期：2026-10-16
> 问题：`style_refs.json` 的图数量如何影响训练速度、显存、效果？
> 方法：读 `_train_v2.py` 实际代码路径 + 在真实函数上实测（GPU 被 v15 占用，故用 CPU 测相对量级）

---

## 0. 结论速览

| 维度 | 参考图数量 N 的影响 |
|---|---|
| **每步训练时间** | **完全无影响（0%）**——refs 只在启动时用一次 |
| **启动开销** | 线性增长，但极小（N=64 时约占整个训练任务的 **0.006%**） |
| **显存峰值** | 线性增长，N=64 时约 +50 MB（8 GB 卡上可忽略） |
| **效果** | N 从 8 → 64 **收敛掉 76% 的采样偏差**；N=8 的随机种子波动是偏差本身的 1.9 倍 |
| **🔴 硬上限** | **N ≤ 64**（size=512 时）。超过直接 `RuntimeError` 崩溃 |

**核心结论**：**加参考图几乎不花时间，但能显著降低风格目标的随机性——上限是 64 张。**

---

## 1. 速度：为什么"零影响"

`_train_v2.py` 中 refs 的**全部消费者都在启动阶段**：

| 行 | 用途 | 时机 |
|---|---|---|
| L413 | `refs = json.loads(style_refs.json)` | 启动，读一次 |
| L419 | Gram 目标（VGG 前向） | 启动，算一次 |
| L420 | `style_mean/std` | 启动，算一次 |
| L440 | `style_quantiles` 分位数 | 启动，算一次 |
| L558+ | **训练循环** | **只用上面算好的张量** |

训练循环里传的是 `style_mean`、`style_std`、`style_q`、`target` —— 都是**预算好的固定张量**。所以：

```
每步耗时 = f(batch, size, 网络)   ← 与 N 无关
```

### 实测启动开销（CPU，size=512）

| N | 解码 | Gram | 统计 | 分位数 | 合计 | 相对 N=8 |
|---|---|---|---|---|---|---|
| 8 | 0.03 s | 3.30 s | 0.03 s | 0.43 s | **3.8 s** | 1.0× |
| 16 | 0.05 s | 6.0 s | 0.07 s | — | 6.1 s | 1.8× |
| 32 | 0.10 s | 13.2 s | 0.13 s | 1.6 s | **13.4 s** | 4.0× |
| 64 | 0.20 s | 24.4 s | 0.26 s | — | **24.9 s** | 7.4× |

线性增长，且**Gram 计算（VGG 前向）占绝对主导**（约 98%）。

### 摊销后：可忽略

以 ukiyo-e v15 实测速率 **1.783 s/step** 为基准（batch 8 / size 512）：

| 任务 | 步数 | 预估总时长 |
|---|---|---|
| ink teacher | 2,500 | ~56 min |
| ink student | 8,000 | **~357 min（约 6 小时）** |

GPU 上 Gram 计算约比 CPU 快 20×，所以：

| N | CPU 启动 | GPU 约 | 占 8000 步任务 |
|---|---|---|---|
| 8 | 3.3 s | 0.16 s | 0.0008% |
| 32 | 13.4 s | 0.67 s | 0.0031% |
| **64** | **24.9 s** | **1.24 s** | **0.0058%** |

**结论：为了稳定目标而增加参考图，时间是免费的。**

### 显存

refs 需在 GPU 上驻留 `(N, 3, 512, 512)` 的 float32 张量：

| N | 张量大小 |
|---|---|
| 8 | 25 MB |
| 32 | 100 MB |
| 64 | **201 MB** |

外加分位数排序的临时副本。在 8 GB 卡上（当前 v15 已用 7.5 GB）**这是需要注意的**——训练时若显存紧张，应优先降 batch 而非砍 refs。

## 2. 🔴 硬限制：N ≤ 64（size=512）

`style_quantiles()`（`_train_v2.py:106-118`）：

```python
s = torch.stack([image_tensor(root/n, size) for n in paths])
s = s.permute(1, 0, 2, 3).reshape(3, -1)      # (3, N*size*size)
return torch.stack([torch.quantile(s[c], q, dim=-1) for c in range(3)])
```

`torch.quantile` 内部会**排序整个轴**，上限 `2**24 = 16,777,216` 元素。size=512 时每张图 262,144 像素：

```
上限 = floor(16777216 / 262144) = 64 张
```

### 在真实函数上验证（非复现，直接调 `tv2.style_quantiles`）

**size=512（水墨计划采用）：**

| N | 通道切片元素数 | 结果 |
|---|---|---|
| 8 | 2,097,152 | ✅ OK |
| 32 | 8,388,608 | ✅ OK |
| **64** | **16,777,216** | ✅ **OK（边界）** |
| **65** | 17,039,360 | ❌ **RuntimeError: quantile() input tensor is too large** |
| 128 | 33,554,432 | ❌ 崩溃 |

**size=256（默认）：**

| N | 结果 |
|---|---|
| 256 | ✅ OK（边界） |
| 257 | ❌ 崩溃 |

**含义**：因为水墨计划设了 `--quantile-weight 0.3 > 0`，这个限制**会真实触发**。
若把 refs 设为 128 张，训练会在**启动阶段直接崩溃**——不是变慢，是起不来。

> 复现命令：调用 `_train_v2.py` 的 `style_quantiles()` 并传 N=65。
> 这与 `_test_128refs.py`（浮世绘时期的调查脚本）的假设相冲突——那个脚本只测 Gram，
> 未经过 `style_quantiles`，所以没暴露此限制。

## 3. 效果：N 到底改善了什么

### 3.1 目标收敛（相对全量 96 张的偏差）

| N | mean\|Δ\| | 相对目标量级 |
|---|---|---|
| 4 | 0.000584 | 30.6% |
| **8** | **0.000526** | **27.6%** |
| 16 | 0.000297 | 15.6% |
| 32 | 0.000170 | 8.9% |
| **64** | **0.000096** | **5.1%** |

（目标量级 = 各层 Gram 平均绝对值 = 0.001905）

### 3.2 随机种子敏感性（两次独立抽样之差）

| N | mean\|Δ\| | 相对 |
|---|---|---|
| 8 | 0.000806 | **42.3%** |
| 16 | 0.000327 | 17.2% |
| 32 | 0.000234 | 12.3% |
| **64** | **0.000115** | **6.1%** |

### 3.3 关键对比：哪个更值得关心

```
|  8 抽样 vs  8 抽样 | = 0.000574   ← 换个随机种子的波动
|  8       vs  全量96 | = 0.000306   ← N=8 的系统偏差
| 64       vs  全量96 | = 0.000074   ← N=64 的系统偏差
```

**随机种子波动（0.000574）是系统偏差（0.000306）的 1.9 倍。**

也就是说：当前 8 张配置下，**"换一批参考图"造成的影响，比"8 张本身不够"更大**。这印证了上一轮的发现——问题不是"图太少"，而是"**抽样的随机性未受控**"。

**N → 64 可消除 76% 的系统偏差**，同时把种子波动压到 6.1%。

### 3.4 不会抬高"地板"（目标可达性）

有人担心更大 N 会让目标变成"谁都不像的平均值"。实测否定：

| N | 留出真迹的 best loss（地板） | 输入照片 | 分离度 |
|---|---|---|---|
| 8 | 0.000019 | 0.000055 | 2.96× |
| 32 | 0.000018 | 0.000056 | 3.13× |
| **64** | **0.000017** | 0.000056 | **3.23×** |

地板略降、**分离度略升**（2.96× → 3.23×）。即更大 N 让"真迹 vs 照片"的区分更清晰，**没有让目标更难达成**。

## 4. 实务建议

| 项 | 建议 |
|---|---|
| **N 取值** | **64**（size=512 的上限，收益已接近饱和） |
| 若想更保守 | 32（已消除 68% 偏差，显存仅 100 MB） |
| **绝对不要** | N > 64（size=512）或 N > 256（size=256）——会崩溃 |
| 抽样方式 | **分层比例抽样**（见 `style_refs_stratified.json`），不要按文件名等间隔 |
| 调整 refs 后 | 必须先确认 `--quantile-weight` 是否 > 0；若为 0 则不受此限制 |

### 与已有 32 张方案的关系

我上一轮生成的 `style_refs_stratified.json` 是 **32 张**：

- 避开 64 上限，留安全余量 ✅
- 消除 68% 系统偏差，稳定性提升 2.0× ✅
- 显存 100 MB，温和 ✅

**若要追求 64 张**：可复用同样逻辑把分配翻倍（水墨 4 / 浅绛 16 / 设色 24 / 青绿 20），
但需注意 64 正好卡在上限，`quantile` 无余量——建议**保持 32，或改用 48**。

---

## 5. 一句话总结

> **参考图数量对训练速度无影响（只在启动时用一次，N=64 时约占任务时长 0.006%）。**
> **它对效果的影响是"降低风格目标的随机性"：N 从 8→64 消除 76% 系统偏差。**
> **但存在硬上限 N ≤ 64（size=512，因 `torch.quantile` 的 2²⁴ 元素限制），超出会启动即崩溃。**
> **推荐 32 张分层抽样**——兼顾稳定性、显存与安全余量。
