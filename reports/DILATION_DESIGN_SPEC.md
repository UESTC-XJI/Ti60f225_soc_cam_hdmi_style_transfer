# Dilation 支持设计规格（**只设计，未实现**）

> 2026-10-28 · 为模型侧可能的膨胀卷积改造预留接口
> **状态：本文件是设计规格，RTL 一行未改。** 实现需等模型侧确认 dilation 取值与层分配。

---

## 一 为什么需要

`reports/FOR_MODEL_BRUSHSTROKE.md` 的结论：笔触画不出来的根因是
**感受野只有 73 输入像素（11.4% 画宽）**，而参考图笔触尺度是 25~50% 画宽。

dilation 是唯一**算力不变**就能扩感受野的手段：

| dilation | 每层覆盖 | 每层贡献（输入 px） | 12 层累计 | 占画宽 |
|---|---|---|---|---|
| **1（现状）** | 3×3 | 8 | **73** | 11.4% |
| **2** | 5×5 | 16 | **~153** | **24%** ✓ |
| **3** | 7×7 | 24 | **~233** | **36%** ✓ |

---

## 二 ⚠ 一个关键发现：改动点不在窗口寄存器

初步以为 dilation 只是把窗口从 3 行加宽到 2d+1 行。**核对代码后发现不是。**

### 当前数据流

```
rowpipe_layer.v:520    reg [WN*8-1:0] w [0:CIW*3-1];      // w[ci*3 + row]
rowpipe_layer.v:544-556  三个 gj 各自从 sb_a/sb_b/sb_c 取新字节
```

- `w` = **3 行 × CIW 通道**，每行 WN*8 bit（WN = PIX+2 = 18）
- **三行是并行喂进来的**（`sb_a/sb_b/sb_c` 来自三路读流）
- 每拍 `adv` 把三行各推进一列

### 窗口 RAM 成本（可忽略）

| 配置 | 窗口位宽 | RAM 块（10 kbit） |
|---|---|---|
| 现状 d=1 | 3 行 × 8 通道 × 144 bit = **3,456 bit** | 0.34 |
| d=2 | 5 行 × ... = **5,760 bit** | 0.56 |
| d=3 | 7 行 × ... = **8,064 bit** | 0.79 |

**增量 ≤ 0.5 块，RAM 余 54 块 ⇒ 完全不是问题。**

### 真正的改动点：**从 DDR 取哪几行**

dilation=d 时，输出行 y 需要输入行 **y−d, y, y+d**（现在是 y−1, y, y+1）。

所以真正要改的是**行地址生成**：

```
rowpipe_frame_driver.v  →  每个输出行取哪三个源行
rowpipe_src_stream.v    →  DDR 突发地址的行走步长
```

### 由此带来的两个后果

1. **行复用被破坏 ⇒ DDR 流量上升**
   现在每个输入行只取一次、靠窗口移位复用。
   dilation=2 时相邻输出行需要的源行集合跨 2 行跳变，
   **要么片上保留 2d+1 行滚动缓冲（每行只取一次），要么重复取行（流量上升）**。

2. **滚动缓冲的 RAM 成本**

   | 方案 | 缓冲 | RAM 块（10 kbit） |
   |---|---|---|
   | 保留 5 行（d=2），每行只取一次 | 5 × 320 px × 8 ch × 8 bit = **102,400 bit** | **10 块** |
   | 不缓冲，重复取行 | 0 | 0，但**读流量约 +50%** |

   **10 块 RAM 在余量 54 之内 ✓**，但读流量不变 ⇒ **首选缓冲方案**。

---

## 三 建议的实现方案（分三步，每步可独立验证）

### Step 1：描述符加 dilation 字段（**零风险**）

`rowpipe_layer` 的描述符是 128 bit，`mk()` 里 **高 22 bit 是 `22'd0` 保留位**
（见 `style_network_rowpipe.sv` 的 `mk` 函数）。

```verilog
// 现:  mk = {22'd0, idf, dstf, srcf, ...}
// 改:  mk = {20'd0, dil, idf, dstf, srcf, ...}   // dil 占 2 bit，1..3
```

- 对现有层 `dil = 2'd1` ⇒ **语义与现在完全相同**
- 面积影响：0（常量）
- 验证：构建后 XLR/RAM/时序应**逐项不变**

### Step 2：行地址生成参数化（**核心改动**）

在 `rowpipe_frame_driver` / `rowpipe_src_stream` 增加：

```verilog
input wire [1:0] dil,          // 1..3
// 行步长：取第 (y-1)*dil, y*dil, (y+1)*dil 行
wire [15:0] row_off0 = (y - 1) * dil;
wire [15:0] row_off1 =  y      * dil;
wire [15:0] row_off2 = (y + 1) * dil;
```

- `dil = 1` 时地址与现在完全相同 ✓
- 需要新增 **(2·dil+1) 行的滚动缓冲**（d=2 时 5 行，10 块 RAM）
- ⚠ **注意行界与 halo**：边缘行的 y±d 会越界，需要行边界钳制
  （现有 `o_row_end` 逻辑要扩展到 ±d 行）

### Step 3：行缓冲滚动（**风险最高**）

把"每行只取一次"的滚动缓冲做出来，保住 DDR 流量不涨。

- RAM +10 块（d=2）
- 改动集中在 `rowpipe_src_stream` 的 FIFO 与行计数
- **这一步最容易引入行对齐 bug**（历史上 A-3 的垂直复制 bug 就是这个类型）

## 四 面积与风险评估

| 项 | 估计 | 依据 |
|---|---|---|
| 窗口寄存器 | **+0.2 块 RAM** | 第二节实测计算 |
| 行滚动缓冲 | **+10 块 RAM**（d=2） | 5 × 320 × 8 × 8 bit |
| **RAM 合计** | **+10.2 块** | 余量 54，**够** ✓ |
| XLR（寻址逻辑） | **+150 ~ +400** | 行地址乘法 + 钳制 + mux，**估算 ±50%** |
| **XLR 余量** | **629** | ⇒ **勉强够但不宽裕** |
| 时序风险 | **中-高** | 改动在 `vid_clk_dvi2` 域（CNN 核，**slack 仅 +0.441 ns**） |
| 全局布局扰动 | **高** | 今天已证明：−418 XLR 的纯删除都能让板子起不来 |

### ⚠ 必须先满足的前提

1. **模型侧确认 dilation 取值与层分配**（哪些层用 d=2，哪些保持 d=1）
2. **先只做 Step 1 + Step 2 的地址参数化（dil=1 恒等）**，构建验证**资源与性能逐项不变**
3. **再做 Step 3**，并准备好回退

## 六 明确不建议的做法

| 做法 | 为什么 |
|---|---|
| 直接把窗口加到 5 行就以为支持了 dilation | **不够**——行地址生成才是核心，窗口加宽只是必要条件 |
| 用重复取行代替滚动缓冲 | 读流量 +50%，而读侧本来就有 8 ms 等待 |
| 一次性把 Step 1/2/3 都做完再上板 | 出问题时无法定位是哪一步；且每次构建 15 分钟 + PnR 是概率性的 |
| 在模型侧还没确认 dilation 取值前就实现 | **可能白做**（d=2 和 d=3 的缓冲深度、地址逻辑都不同） |
