# 方向 A 实测结果：残差层优化收益比预期小

> 日期：2026-10-20
> 方法：**iverilog 状态探针**（`work/ivtest/resid_probe_tb.sv`，未上板）
> 结论：**根因确认成立，但收益只有 5.1%，远低于我此前估计的 2.36×**

---

## ⚠️ 重要更正

**我在 `OFFLINE_OPTIMIZATIONS.md` 里说「残差层慢 2.36×」是对的，但把它当成「可优化 2.36×」是错的。**

| 项 | 我之前说的 | 实测 |
|---|---|---|
| 残差层 vs 无残差层 | 慢 2.36× | ✅ **慢 1.30×**（H=8 严格同尺寸） |
| 可优化收益 | 暗示 2.36× | ❌ **实际 1.30×，其中 100% 是 SKIPWAIT** |
| 折算到板上 CPMS | — | **仅省 1.59 ms（5.1%）** |

## 一、探针实测（H=8 小帧，快速验证机制）

### 全网络状态分布

| 状态 | cycle | 说明 |
|---|---|---|
| WAITROW | **77,744** | 等 core/write 完成（最大项） |
| READWAIT | 34,028 | 等行数据从 DDR 返回 |
| **SKIPWAIT** | **3,936** | **残差层等残差行读** |
| SKIP | 8 | 启动残差读 |
| RUN | 64 | 启动 core/write |
| **合计** | **116,036** | （`dut.cycles` = 116,146） |

### 逐层对比（严格同尺寸）

| layer | 类型 | total | skip | **skipwait** |
|---|---|---|---|---|
| 4 | 无残差 | 3,268 | 0 | 0 |
| **6** | **残差** | **4,254** | 2 | **984** |
| 8 | 无残差 | 3,268 | 0 | 0 |
| **10** | **残差** | **4,254** | 2 | **984** |
| 12 | 无残差 | 3,268 | 0 | 0 |
| **14** | **残差** | **4,254** | 2 | **984** |
| 16 | 无残差 | 3,268 | 0 | 0 |
| **18** | **残差** | **4,254** | 2 | **984** |

### 决定性发现

```
残差层 4254 - 无残差层 3268 = 986 cycle 差额
其中 SKIP + SKIPWAIT = 986 cycle
=> 100.0% 的差额来自残差读等待
```

**根因完全确认**：残差层慢，**100% 是因为 SKIPWAIT（等残差行从 DDR 返回）**。

## 二、收益校准与外推

### 每行残差读延迟

| 项 | 值 |
|---|---|
| H=8 时 SKIPWAIT | 984 cycle |
| 内部层行数（8/4） | 2 行 |
| **每行延迟** | **492 cycle = 4.92 µs @100MHz** |

### 外推到板上 640×480

| 项 | 值 |
|---|---|
| 内部残差层行数（480/4） | 120 行 |
| 残差层数 | 4 |
| **总 SKIPWAIT** | 4 × 120 × 492 = **236,160 cycle** |
| 折算 @148.5MHz | **1.59 ms** |
| 占板上 `CPMS` 31 ms | **5.1%** |

**收益：约 +1.3 fps。**

## 三、诚实的评价：值不值得做？

### 支持做

| 理由 | 说明 |
|---|---|
| **根因 100% 确认** | 探针证明 SKIPWAIT 是唯一多出项 |
| **改动局部** | 只涉及 `style_network.sv` 的 SKIP/SKIPWAIT/RUN 状态 |
| **可与 prefetch 合并** | 残差层正是 prefetch 被排除的 4 层，一次改动两收益 |
| 1.59 ms 也是收益 | 累加到其他优化上有意义 |

### 反对做

| 理由 | 说明 |
|---|---|
| **收益仅 5.1%** | 相比方向 B（上限 −48.8%）小得多 |
| **改动风险不低** | 要改流水线状态机，需重验整数正确性 |
| 有更便宜的替代 | 直接调 `URGENT_OVERRIDES_FAIRNESS` 预期收益更大（读相位 41→32 ms = 11%） |

**结论：方向 A 应降级为「顺手做」，不应作为主攻方向。**

## 五、可执行方案（若做方向 A）

### 改动设计

**当前**（`style_network.sv`）：
```verilog
MAP:  if(ky==3) state <= residual ? SKIP : RUN;
SKIP: rd_address <= skipaddr+y*output_pitch; ... rd_start<=1; state<=SKIPWAIT;
SKIPWAIT: if(rd_done) state <= RUN;          // 纯阻塞
RUN:  ... core_start<=1; wr_start<=1; ...
```

**改法**：把残差读提前到**上一行的 RUN/WAITROW 期间**（类似 prefetch）：

```verilog
// 在 RUN 里，若本层是残差层，提前预取 y+1 行的残差
if(residual && y+1<oh && !rd_busy) begin
  rd_address <= skipaddr + (y+1)*output_pitch;
  rd_pixels  <= ow; rd_channels <= co;
  rd_start   <= 1; prefetch_active <= 1;
end
```

**风险**：
- 需要额外的残差行缓冲（1 行 × ow × co 字节）
- RAM 仅剩 8 块（248/256），**可能放不下**
- 需重验整数输出与 oracle 一致

**工作量**：1–2 天（含仿真验证）

## 七、我的建议

**不建议现在做方向 A。** 理由：

1. **收益只有 5.1%**，而方向 B 上限 48.8%
2. **改动风险不低**（流水线状态机 + 可能的 RAM 不足）
3. **有更便宜的替代**：`UOF=1→0` 已编译好，预期收益 11%

**建议顺序**：
1. **先上板验证已编好的 `UOF=0` bit**（零额外工作，预期 −11% 读相位）
2. 若还有余力，做方向 B（1×1 用满 taps，上限 −48.8%）
3. **方向 A 留作最后的小优化**，或与 prefetch 扩大合并做
