## 三、根因：AMP GradScaler **死亡螺旋**

### 直接证据：scaler 轨迹

| step | scale |
|---|---|
| 500 | **128** |
| 1000 | **0.0625**（减半 11 次） |
| 1500 | **9.3e−10**（减半 26 次） |
| 2000 | **6.6e−24**（减半 47 次） |
| 2500 | **1.5e−36**（减半 42 次） |

**从 128 到 1.5e−36 共减半约 126 次 ≈ 126 次 inf 事件**（平均每 10–12 步一次）。

### 机制

```
GradScaler 默认 growth_interval = 2000
  -> 每次 backward 出现 inf，scale 减半
  -> 连续 2000 步无 inf，scale 才翻倍
  实测 inf 每 10-12 步一次 -> 永远无法积累 2000 步
  -> scale 单调下降，永不恢复
  -> scale 1.5e-36 时，fp16 梯度全部下溢为 0
  -> scaler.step() 看到「有限梯度」（全 0），不跳过
  -> optimizer 计数继续涨，权重却完全冻结
```

### 为什么这是"静默失败"

损失函数**看起来正常**（6.8–15.0 波动，未归零），验证**照常运行**，
**没有任何报错** —— 只有对比权重 hash 才能发现。

## 四、⚠️ 我的因果推断被二分实验推翻

### 我的错误推断

我观察到「**只有 v3 崩塌**，v1/v2 健康」，便推断**是 v3 的配置差异**
（`contrast-absolute 0.2730`）导致。

### 二分实验结果（各 700 步）

| 变体 | 700 步后 scaler |
|---|---|
| **V1（v3 精确配置）** | **128 健康** ✅ |
| V2（ratio+24） | 256 健康 |
| V3（abs+8） | 128 健康 |
| **V4（v2 精确配置，对照）** | **64（降幅最大）** |

**v3 的配置在 700 步时完全健康，对照组 v2 反而降幅最大。**

**→ 崩塌是随机事件，不是配置导致。**我犯的是本项目第 7 次同类错误：
**从单次观测推因果**（未做对照实验）。

### 已排除的假设（全部实测）

| 假设 | 实测结果 |
|---|---|
| forward 产生 nan/inf | ❌ 全部有限（y/sat/dark-hf/grain/L 均无 nan） |
| gram 在 fp16 溢出 | ❌ 最大 0.66 vs fp16 max 65504；且 **gram 已强制 fp32** |
| 逐项梯度 inf | ❌ 各项 0/54 bad |

| eval 模式未恢复 | ❌ `model.train()` 在每步循环开头（L642） |
| **统计推断（配置差异）** | ❌ **被二分实验推翻** |

## 五、修复（已实施并验证）

```python
# 1. 降低 init_scale + 缩短 growth_interval，让 scale 能恢复
scaler = torch.amp.GradScaler('cuda', init_scale=256.0, growth_interval=200)

# 2. 崩塌时【显式报警】，不再静默训练
_sc = float(scaler.state_dict().get('scale', 1.0))
if _sc < MIN_SCALE and scale_collapse_step is None:
    print('WARNING scaler collapse at step %d: scale=%.3e. ...' % (step, _sc))

# 3. scale 写入 train.jsonl，使崩塌在数据中可见
row = {'step': step, 'scale': _sc, ...}
```

**验证**：150 步测试运行，`scale` 稳定在 256→128，**无 WARNING**。

**关键改进**：即使将来再发生，**会在日志中报警**，不再需要靠对比权重 hash 才能发现。
