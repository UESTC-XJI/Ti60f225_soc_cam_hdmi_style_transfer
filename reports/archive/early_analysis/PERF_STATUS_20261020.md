## 二、可确认的改善

### 1. 显示读流量减半 —— 归因明确

| | DRB |
|---|---|
| 历史（双面板） | 9,392,768 / 1.018 s |
| **本次（单面板）** | **4,695,168 / 1.018 s** |
| **变化** | **−50.0%** |

**这正是我们 `style_display.sv` 单面板改动的直接效果**
（历史版 `h 260..1540` = 1280 宽；我们 `IMG_X0=580` + 640 = 单次读）。

历史 README 自己记录了双面板的代价：「约 147.462 MB/s 显示读流量」。
**我们减半后约 73.7 MB/s。**

### 2. UF 从 142,426 → **0**（数量级改善）

| 版本 | UF 累计 | DUF（1.018s 增量） |
|---|---|---|
| 早期诊断版 | **142,426** | 1,873 |
| 早期诊断版（另一轮） | **425,798** | 4,194 |
| release_display_deadline | 16 | 0 |
| **本次** | **0** | **0** |

**注意**：`release_display_deadline` 那版（urgent 读保留 + 双面板）**已把 UF 降到 16**，
所以**大部分 UF 改善来自那版**，不是本次。
本次从 16 → 0 是**进一步的**改善，量级小。

### 3. FAULT 4 → 0

历史两轮均为 FAULT 4，本次 **0**。

## 三、⚠️ 需要打折看的项

### 1. NN fps **没有提升**（12 vs 历史 14–15）

| 版本 | NN |
|---|---|
| hardware_20261012（双面板，无 urgent） | **15** |
| reflash_20261012（双面板，无 urgent） | **14** |
| release_display_deadline（双面板 + urgent） | 10 |
| **本次（单面板 + 我们全部改动）** | **12** |

**结论**：本次 12 fps **低于**最早期的 14–15 fps。

**原因分析（不可直接归因）**：
- `release_display_deadline` 为保显示把 NN 从 15 降到 10（其 README 明确：
  「NN 吞吐低于原诊断版的约 14~15 fps；这是优先保证显示期限的代价」）
- 本次 12 fps 处于 10 与 15 之间
- **我们的 2 个取用文件（ROM/位宽）不改变 CNN 网络，理论不影响 fps**

**所以 12 fps 更可能来自：
① 单面板减少了显示竞争（相对 10 是 +20%）；
② 但仍未回到 15（因为保留了 urgent 优先级策略）。**

**诚实标注**：**无法把 12 fps 单归因于本次改动**，因为显示仲裁策略在历史版本间也变了。

### 2. AR 23% 高于早期的 9%

| 版本 | AR（CNN 等读） |
|---|---|
| 早期两轮 | 9% |
| release_display_deadline | 36% |
| **本次** | **23%** |

本次 23% 优于 release 的 36%，但**劣于**早期的 9%。
同样受显示仲裁策略影响，**不能单独归因**。

## 四、归因总表（诚实）

| 改善 | 可归因？ | 归因给谁 |
|---|---|---|
| **DRB 减半（−50%）** | ✅ **可归因** | **我们的单面板 `style_display.sv`** |
| UF 142,426 → 16 | ✅ 可归因 | **`release_display_deadline` 的 urgent 策略**（历史版） |
| UF 16 → 0 | ◐ 量级小 | 本次（含单面板减少竞争） |
| FAULT 4 → 0 | ◐ | 本次 |
| **NN fps 12** | ❌ **不可归因** | 显示仲裁策略在历史版本间已变 |
| AR 23% | ❌ 不可归因 | 同上 |
| **2 个取用文件的性能影响** | ❌ **无证据** | 不改 CNN 网络，理论不影响 fps |

**关键结论**：
**我们本次真正、可确证的性能收益是「显示读流量减半」（−50%）。**
**NN fps 没有提升**（12 vs 历史 14–15/10），且无法归因。
