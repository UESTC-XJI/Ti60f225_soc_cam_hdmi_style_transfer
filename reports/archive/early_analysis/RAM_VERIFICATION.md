# RAM 核实结论：做 3×3 预取是否可行

> 日期：2026-10-20
> 方法：**实测 res.csv RAM 分布 + 4-bank 变体综合实验**
> 结论：**RAM 不是主要障碍，XLR 才是；但仍需真实接线才能最终确认**

---

## 一、实测数据（res.csv，UOF=1 基线）

### 全局资源

| 资源 | 使用 | 总量 | **余量** |
|---|---|---|---|
| **Memory Blocks** | **237** | 256 | **19** |
| XLR | 55,718 | 60,800 | **5,082** |
| DSP | 140 | 160 | 20 |

### style_demo 内部 RAM 分布（关键）

| 模块 | RAM 块 | 说明 |
|---|---|---|
| `style_demo` 合计 | **121** | |
| └ `mac:style_mac8x12` | **112** | **占 93%** |
| └ `network` 其它 | 5 | |
| └ `dma:style_axi_rows` | 2 | |
| └ **`core:style_row_core`** | **1** | **行缓冲所在** |

### ⚠️ 关键矛盾：行缓冲 245,760 bit 却只占 1 块

现有行缓冲声明（`style_row_core.sv`，标记 `block_ram`）：

```verilog
row0lo/row1lo/row2lo : 64 bit  x 640  = 40,960 bit/bank
row0hi/row1hi/row2hi : 128 bit x 320  = 40,960 bit/bank
一个 bank 合计 81,920 bit，3 个 bank = 245,760 bit
```

**但 res.csv 显示 `core` 只用 1 块 RAM。**

- 245,760 bit / 1 块 → 每块 245,760 bit，**不可能**（Ti60 总容量才 256 块 × ~10 kbit）
- **结论：行缓冲实际没有用 block RAM**，被映射到 **LUTRAM / 分布式 RAM / FF**

---

## 二、4-bank 综合实验

### 实验设计
在 `style_row_core.sv` 添加第 4 个 bank 声明（`row3lo/row3hi`），编译看资源变化。

### 结果

| 项 | 基线（3 bank） | **4 bank** | 变化 |
|---|---|---|---|
| **Memory Blocks** | 237 / 256 | **237 / 256** | **0** |
| XLR | 55,718 | **55,857** | **+139** |

### 解读

**RAM 完全没变（237 → 237）**，说明：
1. 新加的 bank 未被综合器认作 block RAM
2. 与上面「行缓冲不在 block RAM」的结论一致
3. **XLR 只 +139**，说明综合器把未接线的声明基本优化掉了

**⚠️ 这个实验不能作为最终结论** —— 因为声明未接线，被优化了。
**必须真实接线后再综合**，才能测出实际增量。

---

## 三、初步结论

### RAM 不是障碍（很可能）

| 判据 | 说明 |
|---|---|
| 余量 19 块 | 若行缓冲真不用 block RAM，加 bank 也**不消耗 RAM** |
| 实验未显示 RAM 增长 | 4-bank 版 RAM 仍 237 |
| **行缓冲用 LUTRAM** | 245,760 bit 只占 1 块只能这样解释 |

### XLR 可能吃紧

| 判据 | 说明 |
|---|---|
| 余量 5,082 XLR | |
| 一个 bank = 81,920 bit | |
| 若用 LUTRAM 实现 | 81,920 bit / 6 bit-per-LUT ≈ **13,653 LUT** ← **超余量** |
| 若用 FF 实现 | 81,920 FF ← 更超 |

**但 LUTRAM 的映射效率不一定按 6 bit/LUT**，需实测。

---

## 四、真正的优化机会（不需要新 bank）

**重新审视**：3×3 层的行缓存**已有 3 bank**，理论上 y 行用 {y-1,y,y+1}，y+1 行用 {y,y+1,y+2} —— **只需新读 y+2 一行**。

**所以 3×3 层不需要第 4 个 bank 就能预取！**

| 场景 | 需要的 bank |
|---|---|
| 当前行 y 计算中 | {y−1, y, y+1} |
| 预取 y+2（供下一行用） | 需要 1 个额外位置 |

**关键**：3 bank 在 y 行使用时全被占用，**没有空闲放 y+2**。
所以确实需要第 4 个 bank，或**等 y 行计算完成后再预取**（但那就晚了）。

---

## 五、诚实的核实结论

| 问题 | 答案 |
|---|---|
| **RAM 够吗？** | **很可能够**（行缓冲不用 block RAM，实测加 bank 后 RAM 仍 237） |
| **XLR 够吗？** | ⚠️ **可能不够**（一个 bank 81,920 bit，仅剩 5,082 XLR） |
| **能确定吗？** | ❌ **不能** —— 4-bank 实验未接线，需真实实现后综合 |
| **是否需要新 bank？** | ✅ **需要**（3 bank 在计算时全占用） |

## 六、建议的下一步

### 选项 A：真实实现 3×3 预取（推荐但工作量大）

1. `style_row_core.sv` 加第 4 个 bank 并**真实接线**
2. `style_network.sv` 改 prefetch 条件支持 `kernel3`
3. iverilog 验证整数正确性
4. 综合看 XLR/RAM 是否够
5. 上板验证

**预期收益**：若 3×3 层（12 个，占 52% 周期）的 DDR 等待被隐藏一半 → **总周期约 −25%**

**风险**：XLR 可能超（5,082 余量 vs 需数千 LUT）

### 选项 B：先上板验证已编好的 UOF=0（零成本）

| 项 | 值 |
|---|---|
| 工作 | **0**（bit 已编好） |
| 预期 | 读相位 41 → 32 ms（−22%） |
| 风险 | 可能欠载（有回滚 bit） |

### 选项 C：降低 DDR 读延迟本身

| 方向 | 说明 |
|---|---|
| 加长 burst | 当前 max 32 beat |
| 提高时序效率 | 需重做时序收敛 |
| 提高 DDR 频率 | 高风险 |

## 七、我的建议

**先做选项 B**（零成本，已编好），**再评估选项 A**。
